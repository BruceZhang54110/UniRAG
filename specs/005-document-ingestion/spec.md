# Feature Specification: 文档摄取与双粒度切片

**Feature Branch**: `005-document-ingestion`

**Created**: 2026-10-01

**Status**: Draft

**Input**: User description: "基于当前架构继续设计文档切片逻辑，依然使用langchain4j 最佳实践，如果不清楚可以先研究"

## Clarifications

### Session 2026-10-01

- Q: 摄取管线的配置形态应采用哪种？ → A: 租户内可配置任意多条**命名摄取管线**（key 租户内唯一），每条管线独立声明切片策略、目标向量存储资源、嵌入模型资源；粗/细双粒度是"配置两条管线"的自然结果，而非平台硬编码的两条流水线。
- Q: 本期是否交付文档上传 HTTP 接口？ → A: 不交付。本期交付摄取核心服务（同进程内 API 调用 + 自动化测试验证）；HTTP 上传接口与检索问答接口同属后续 feature。
- Q: PDF/Office 等二进制格式解析是否纳入本期？ → A: 不纳入。本期支持纯文本/Markdown 内容摄取，解析器按可插拔 SPI 设计（对齐 langchain4j DocumentParser 生态），二进制格式（PDF/Office，依赖 Apache Tika/PDFBox/POI 等独立模块）留待后续 feature。

## User Scenarios & Testing *(mandatory)*

> **本期范围说明**：交付"文档摄取"——文档进入系统后按租户配置的摄取管线完成解析、切片、向量化、入库，并保存文档/切片元数据可追踪。检索、问答、HTTP 接口、二进制格式解析不在本期。

### User Story 1 - 文档按租户配置切片入库 (Priority: P1)

开发者调用摄取服务提交一份文档（标题 + 文本内容）到指定租户，系统按该租户配置的切片策略将文档切分为片段，调用该租户自己的嵌入模型将片段向量化，写入该租户自己的向量表；同时保存文档与切片的元数据（归属租户、序号、文本、向量回链），之后可通过元数据查到这份文档被切了多少片、存到了哪里。

**Why this priority**: 这是 RAG 链路"索引侧"的完整闭环——004 交付了向量存储的就绪状态，但没有文档进不来任何内容；没有摄取，检索问答（006）无米下锅。

**Independent Test**: 单租户集成测试：配置一条摄取管线（切片上限 + 目标向量表 + 嵌入模型），摄取一篇足够长的文档，断言——切片元数据记录数与向量表记录数一致且逐片可回链；用与某片段语义贴近的查询向量检索，能命中该片段；换租户检索不到。

**Acceptance Scenarios**:

1. **Given** 租户配置了切片上限为 N 的摄取管线，**When** 摄取一篇长文档，**Then** 文档被切为若干不大于 N 的片段，每个片段的向量都写入该管线指向的租户向量表，业务表中每个片段有对应的元数据记录且能关联到向量表中的记录。
2. **Given** 两个租户各自配置了自己的管线和向量表，**When** 同一篇文档分别被两租户摄取，**Then** 两租户的切片与向量各自落在自己的表里，任一租户检索不到对方的内容。
3. **Given** 文档短于切片上限，**When** 摄取，**Then** 产生至少一个片段，不报错。
4. **Given** 摄取完成后，**When** 查询文档状态，**Then** 能看到成功状态、片段总数、所属管线信息。

---

### User Story 2 - 粗/细双粒度（多管线）同时摄取 (Priority: P2)

租户同时配置"粗粒度"与"细粒度"两条摄取管线（不同切片上限，指向不同向量表、可用不同嵌入模型与维度）。一份文档一次摄取，两条管线各自执行：粗粒度产出少量大片段，细粒度产出多个小片段，分别写入各自的向量表——为后续"粗排定位文档、细排定位段落"的检索策略提供数据基础。

**Why this priority**: 这是用户在 004 澄清会话中明确提出的需求（"文档要支持同时切分粗粒度的和细粒度的"），也是多表租户能力（004 contracts §5）的第一个真实消费方。依赖 US1 的摄取闭环，但管线互相独立可单独验收。

**Independent Test**: 双管线集成测试：租户配置 coarse（大上限）与 fine（小上限）两条管线指向两张不同向量表，摄取一篇文档，断言——两张表都写入了数据；粗表片段数少于细表；粗表片段文本长度大于细表；两表检索互不串数据。

**Acceptance Scenarios**:

1. **Given** 租户配置 coarse（上限 1000）与 fine（上限 200）两条管线，**When** 摄取一篇长文档，**Then** 粗管线产出少量大片段写入粗表，细管线产出多个小片段写入细表，一次调用两表均就绪。
2. **Given** 两条管线配置了不同嵌入模型/维度，**When** 摄取完成，**Then** 各表向量维度与各自管线声明的模型输出一致（写入时维度不匹配会按该管线失败处理，不影响另一条管线）。
3. **Given** 一条管线因目标向量表不可用而失败，**When** 摄取完成，**Then** 另一条管线照常成功，文档状态如实反映部分成功与失败明细。

---

### User Story 3 - 摄取的可观测、故障隔离与重复摄取语义 (Priority: P3)

摄取过程对运维与调用方透明：每条管线的执行结果（成功/失败/片段数）可查询；任何一条管线失败不影响其他管线；同一文档重复摄取有明确的确定语义（按内容识别，重摄取即替换旧数据），不产生重复碎片。

**Why this priority**: 生产摄取必然面对重试、更新文档、部分失败三类场景；但作为"索引侧"的运维保障，它不妨碍 US1/US2 的主链路，列 P3。

**Independent Test**: 故障与重摄取集成测试：构造一条失败管线 + 一条成功管线断言隔离与明细；同一文档内容重复摄取两次断言数据被替换而非翻倍；内容变化后重摄取断言旧片段被清理、新片段生效。

**Acceptance Scenarios**:

1. **Given** 文档已摄取完成，**When** 以完全相同的内容再次摄取，**Then** 系统识别为重复摄取，替换而非追加，向量表与元数据记录数不翻倍。
2. **Given** 文档内容发生变化后重新摄取，**When** 完成后，**Then** 旧切片（含向量）被清理，新切片生效，文档状态指向最新版本。
3. **Given** 多条管线中一条失败（如目标表被删除），**When** 摄取完成，**Then** 成功管线数据保留，失败管线有明确原因记录，整体状态为"部分成功"且可查询。

---

### Edge Cases

- 文档为空或仅空白字符——明确失败并给出可读原因，不产生半截记录。
- 单个自然段超长（超过切片上限数倍）——必须被继续切分到上限以内，而非保留超大片段。
- 向量表在摄取中途被删/不可用——已写入的该管线数据与其余管线数据如何处理，语义在 plan 阶段定义（倾向：该管线已写片段清理，其余管线保留）。
- 嵌入模型资源不存在或未配置——该管线失败，其他管线不受影响。
- 摄取中途进程重启——文档状态不得停留在"进行中"误导后续重试（启动时对中断状态的恢复语义在 plan 阶段定义）。
- 并发摄取同一文档——同一租户同一文档的并发摄取必须串行化或以确定性结果收尾（不产生双份数据）。
- 切片重叠（overlap）导致相邻片段共享文本——属预期行为，重叠大小由管线配置。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供摄取服务：接收（租户、文档标识信息、文本内容），按该租户**所有已启用的摄取管线**各执行一遍"切片→向量化→写入对应向量表"，并持久化文档与切片的元数据。
- **FR-002**: 每条摄取管线 MUST 独立可配置：切片策略（上限大小、重叠大小）、目标向量存储（引用租户 EMBEDDING_STORE 资源 key）、嵌入模型（引用租户 EMBEDDING_MODEL 资源 key）、启用状态；配置在租户内按 key 唯一。
- **FR-003**: 每个写入向量表的片段 MUST 携带可回链的元数据（文档标识、管线 key、片段序号），业务表中的切片记录 MUST 能关联到对应向量记录。
- **FR-004**: 管线之间 MUST 故障隔离：单条管线失败（模型缺失、表不存在、维度不匹配、写入失败）不得影响其他管线；失败原因 MUST 可查询。
- **FR-005**: 文档 MUST 有明确的生命周期状态（如进行中/成功/部分成功/失败），片段数与管线执行结果 MUST 可查询。
- **FR-006**: 重复摄取 MUST 按内容识别：同内容重摄取 = 替换旧数据（含旧向量），内容变更重摄取 = 清理旧版本后写入新版本；任何情况下不得产生重复碎片。
- **FR-007**: 同一文档的并发摄取 MUST 以确定性结果收尾（串行化或等价机制），不得产生双份数据。
- **FR-008**: 切片大小 MUST 有上限保证：任何片段都不得超过管线配置的上限（超长自然段继续向下切分）。
- **FR-009**: 全部行为 MUST 可在 `./mvnw test` 中以真实数据库集成测试验证，向量化 MUST 可使用本地确定性嵌入模型替身（不依赖外部模型服务凭据）。
- **FR-010**: 任何日志与查询输出 MUST NOT 包含 api-key 等敏感配置（FR-008 红线延续）。

**明确不在本期范围**（后续 feature 交付）：

- 检索、检索增强问答、重排（006）
- 文档上传/管理 HTTP 接口（006）
- PDF/Office 等二进制格式解析（解析器 SPI 预留，Apache Tika 等独立模块引入在后续 feature 决策）
- 文档删除/归档等生命周期管理（本期仅有"重摄取替换"语义）
- 按定时任务/消息队列的异步批量摄取编排（本期为同步摄取服务）

### Key Entities *(include if feature involves data)*

- **文档（Document）**: 一份被摄取的文本内容。属性：标识、所属租户、标题/来源、内容指纹（用于重复识别）、状态、当前版本、片段总数、创建/更新时间。
- **摄取管线（Ingestion Pipeline）**: 租户内一条命名的摄取配置。属性：所属租户、key、切片上限、重叠大小、目标向量存储资源 key、嵌入模型资源 key、启用状态。
- **文档切片（Chunk）**: 文档经一条管线切出的一个片段。属性：所属文档、所属管线、序号、文本内容、大小计量、向量记录回链标识、创建时间。
- **管线执行记录（Ingestion Run）**: 一次摄取中一条管线的执行结果。属性：所属文档、管线、结果状态、片段数、失败原因、完成时间。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 调用方一次调用即可使文档在租户配置的所有管线上就绪；单管线摄取一篇 5000 字文档（细粒度 10 片段以内）在常规开发环境 10 秒内完成（含向量化，本地替身模型）。
- **SC-002**: 100% 的切片可按业务记录回链到向量记录，回链断链（有元数据无向量或有向量无元数据）测试用例通过率为 0。
- **SC-003**: 双管线摄取中，任一管线失败的隔离测试通过率为 100%，成功管线数据零丢失。
- **SC-004**: 同一文档重复摄取任意次数，向量与元数据记录数稳定（替换语义），重复数据测试用例通过率为 0。
- **SC-005**: 双租户同内容摄取的隔离测试通过率 100%——任一租户检索不到对方文档的任何片段。
- **SC-006**: 全部自动化测试在无外部模型凭据环境可运行且全绿。

## Assumptions

- 摄取基于 langchain4j 官方摄取管线惯例（研究来源：langchain4j RAG 教程）——解析器（DocumentParser，本期文本/Markdown）、递归切片器（DocumentSplitters.recursive：段落→句子→词的层级切分，上限/重叠以 token 计量、Tokenizer 可插拔）、片段转换（TextSegmentTransformer，如向片段文本前缀来源标识以提升检索质量）、批量向量化（embedAll 分批）、写入 EmbeddingStore；编排优先复用 `EmbeddingStoreIngestor` 的能力与惯例，租户资源（模型/向量表）经 003 Router 按管线声明的 key 注入。
- 存储形态延续已定决策：业务数据（文档/管线/切片/执行记录）与向量数据同库存储（uni_rag_db），业务表按租户字段归属；向量部分按 004 交付的"每租户 EMBEDDING_STORE 资源一张表"落地——粗细粒度即同一租户两条管线指向两个资源 key 的两张表。
- 摄取管线配置的持久化形态（独立业务表 vs 003 资源体系的新类型）由 plan 阶段决策，本 spec 不绑定。
- 文档输入形态为本期约定的（标题 + 文本内容 + 可选来源标识）；文件系统/URL 加载（langchain4j DocumentLoader 生态）留待 HTTP 接口 feature 一并设计。
- 中文文本的 token 计量采用可插拔 Tokenizer（具体实现在 plan 阶段从 langchain4j TokenCountEstimator 生态中选定；默认方案需对中文有合理近似）。
- 文档内容指纹用于重复识别（算法 plan 阶段定，要求：同内容必同指纹、不同内容指纹冲突概率可忽略）。
- 同步摄取模型：一次调用内完成全部管线；异步编排不在本期。
