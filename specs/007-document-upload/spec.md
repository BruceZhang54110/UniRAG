# Feature Specification: 文档上传与文件存储

**Feature Branch**: `007-document-upload`

**Created**: 2026-10-02

**Status**: Ready for review

**Input**: User description: "开发文档上传接口和逻辑，以及 Apache OpenDAL 整合 pg 存储文件。并和文分片逻辑连起来，用于整个rag 链路"

## Clarifications

### Session 2026-10-02

- Q: 原文文件保存在哪里？ → A: **存 PostgreSQL（bytea）**，通过 Apache OpenDAL 作为存储抽象层接入，配置驱动可在后续切换对象存储后端，不新增外部中间件（项目轻量级目标）。
- Q: 本期支持哪些文件格式？ → A: 仅纯文本 / Markdown（与 005 摄取能力对齐）；PDF/Office 等二进制解析沿用 005 决策留待后续 feature，本期明确拒绝并返回可读原因。
- Q: 上传后是否自动触发摄取？ → A: 是。上传成功即触发该租户全部已启用摄取管线（005 能力），一次调用完成"上传→存储→切片→向量化"全链路。
- Q: 断点续传采用哪种协议形态？ → A: **轻量固定分块**——文件按固定大小切块，每块独立上传、独立可重传；全部块到齐后服务端拼装入库。分块先落 PG 暂存表（随主库持久），不引入 S3 multipart / tus 等外部协议。
- Q: 一次性上传与分块上传的 API 形态？ → A: **并存、按大小自动路由**——小文件（≤阈值，默认 10MB）走一次性 multipart 接口保持单调用闭环；大文件走分块三阶段协议（初始化→分块→完成）。两条路径共用同一个"拼装入库→触发摄取"核心。

## User Scenarios & Testing *(mandatory)*

> **本期范围说明**：交付"上传侧"——文档上传/下载 HTTP 接口、原文文件存储（OpenDAL + PG bytea）、上传与 005 摄取管线的自动衔接。检索/问答（006）、二进制格式解析（后续 feature）不在本期。

### User Story 1 - 上传文档并自动完成摄取入库 (Priority: P1)

开发者通过 HTTP 接口向指定租户上传一份纯文本/Markdown 文档（标题 + 文件），系统校验类型与大小后把原文持久化存储，登记文档与文件元数据，随即触发该租户全部已启用摄取管线完成切片与向量化入库，最终返回文档标识与摄取状态；上传完成后用检索接口即可命中该文档的片段，整条 RAG 索引链路闭环。

**Why this priority**: 005 交付了摄取核心（应用内 API）、006 交付了检索问答（HTTP），唯独"文档怎么进来"缺最后一块——没有上传入口，RAG 链路无法被外部用户驱动。这是全链路闭环的最短缺口，P1。

**Independent Test**: 单租户集成测试：通过上传接口 POST 一篇足够长的 Markdown 文档 → 断言返回文档标识与摄取成功状态、`document`/`document_chunk` 记录与向量表记录一致（005 已有断言口径）；随后用 006 检索接口查询与该文档语义贴近的问题 → 能命中片段并携带正确来源元数据。

**Acceptance Scenarios**:

1. **Given** 租户配置了已启用的摄取管线，**When** 上传一份格式合规的 Markdown 文档，**Then** 原文被持久化存储、文档与文件元数据入库、该租户全部已启用管线完成切片与向量化，响应返回文档标识与逐管线摄取结果。
2. **Given** 两个租户各自上传同一篇文档，**When** 分别调用各自租户的上传接口，**Then** 两租户的原文与切片各自隔离存储，任一租户检索不到对方内容（租户隔离用例通过率为 0 泄漏）。
3. **Given** 文档短于切片上限，**When** 上传，**Then** 产生至少一个片段、不报错，文档状态为成功。
4. **Given** 上传请求缺少租户标识或租户不存在，**When** 调用上传接口，**Then** 返回明确的 4xx 错误与可读原因，不产生任何存储与元数据残留。

---

### User Story 2 - 下载原文与查询文档信息 (Priority: P2)

开发者通过 HTTP 接口按文档标识获取原文文件（字节完整、文件名与类型正确），并可查询文档列表/详情（标题、状态、片段数、文件大小、格式、上传时间）。这是文档管理的最小只读面，也是核对"上传的东西存对了没有"的直接手段。

**Why this priority**: 下载/查询不是索引链路的必需环节，但没有它上传就成了单向黑洞——用户无法验证、无法复核原文，运维无法核对存储正确性。P2。

**Independent Test**: 集成测试：上传文档 → 调用下载接口 → 断言返回字节与上传内容逐字节一致、文件名/类型元信息正确；调用文档详情接口 → 断言状态、片段数、文件大小与实际入库一致。

**Acceptance Scenarios**:

1. **Given** 文档已上传成功，**When** 调用下载接口，**Then** 返回与上传内容逐字节一致的原文，响应携带正确的文件名与内容类型。
2. **Given** 文档标识不存在或属于其他租户，**When** 调用下载接口，**Then** 返回明确的 404/403 语义，不泄漏其他租户文档的存在性信息。
3. **Given** 租户已上传多篇文档，**When** 查询文档列表，**Then** 只返回本租户文档，按上传时间倒序，分页可遍历全部。

---

### User Story 3 - 重复上传语义与存储故障边界 (Priority: P3)

同一租户重复上传内容完全相同的文件：系统按内容指纹识别，不产生重复存储与重复切片（沿用 005 的 NOOP/替换语义）；存储环节失败（如数据库不可用）不产生半截元数据记录；超限文件、非法类型在上传入口处被明确拒绝。

**Why this priority**: 这是上传侧的运维保障与幂等性，生产环境必然遇到重试与失败，但不妨碍 US1/US2 的主链路，P3。

**Independent Test**: 集成测试：① 同内容二次上传 → 断言文件与切片记录数不翻倍、版本语义与 005 一致；② 内容变化后重传同名文件 → 旧文件版本被替换、新内容生效；③ 模拟存储失败（如表不存在）→ 断言无半截 `document` 记录、错误原因可读且不含敏感配置。

**Acceptance Scenarios**:

1. **Given** 同（租户、文档标题、内容指纹）的文件已存在，**When** 再次上传，**Then** 系统识别为重复上传，文件与切片数据不翻倍，响应如实反映 no-op 语义。
2. **Given** 同名文件内容发生变化后重新上传，**When** 完成后，**Then** 旧版本原文被替换、切片与向量按 005 替换语义清理后重建。
3. **Given** 文件超过大小上限或类型不被支持，**When** 上传，**Then** 请求在入口处被拒绝，返回可读原因与上限信息，不产生任何残留记录。
4. **Given** 原文存储写入失败，**When** 上传完成（失败），**Then** 不产生无文件的空文档记录，失败原因可查询且不含密钥等敏感配置。

---

### Edge Cases

- 上传文件为空（0 字节）或仅空白字符——明确失败并给出可读原因（与 005 空文档语义一致）。
- 文件大小恰好等于上限——边界值必须被接受。
- multipart 请求格式非法/缺文件字段——入口处 4xx，可读原因。
- 文件名包含路径分隔符、特殊字符或非 UTF-8——安全归一化后入库，不造成路径穿越或存储键注入。
- 并发上传同（租户、标题、内容）——结果确定，不产生双份数据（复用 005 并发摄取语义）。
- 原文存储成功但摄取全部管线失败——文档如实记录失败状态，原文保留可查可重试。
- 摄取中途进程重启——沿用 005 启动恢复语义，上传接口不引入新的中断窗口。
- 分块上传中途断网——重新上传缺失/失败的块即可续传，已收块不得要求重传或重复落库。
- 完成请求到达时存在缺失/损坏的块——拒绝完成并返回明确的缺失块清单。
- 上传会话长期未完成——过期会话及其暂存块可被安全清理（默认保留 24 小时，可配置），清理不影响已完成文档。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供文档上传 HTTP 接口（一次性 multipart，面向小文件，阈值可配置、默认 10MB）：接收（租户标识、文档标题、文件），校验通过后置持久化存储、登记文档与文件元数据，并自动触发该租户全部已启用摄取管线；响应 MUST 包含文档标识与逐管线摄取结果。
- **FR-010**: 系统 MUST 提供断点续传能力（轻量固定分块，面向超过 FR-001 阈值的文件）：初始化上传会话 → 分块上传（每块独立可重传、乱序可补传）→ 完成时服务端校验全部块到齐并拼装入库后触发摄取；块大小与单文件上限 MUST 可配置（块默认 5MB、单文件默认 50MB）。FR-001 与 FR-010 MUST 共用同一个"拼装入库 → 触发摄取"核心。
- **FR-002**: 系统 MUST 通过统一的存储抽象层（Apache OpenDAL）读写原文文件；v1 后端 MUST 为 PostgreSQL（bytea），存储后端 MUST 由配置切换，业务代码不感知后端差异。
- **FR-003**: 上传 MUST 校验文件类型（v1 仅纯文本/Markdown，按扩展名+内容双重判断）与大小（上限可配置，默认 50MB）；不合法请求 MUST 在入口处被拒绝并返回可读原因，不产生任何存储或元数据残留。
- **FR-004**: 系统 MUST 提供原文下载 HTTP 接口与文档列表/详情查询接口；下载 MUST 返回与上传内容逐字节一致的数据，查询/下载 MUST 严格按租户隔离，跨租户访问返回明确的 404/403 语义。
- **FR-005**: 重复上传 MUST 沿用 005 语义：同（租户、文档标识、内容指纹）→ no-op；内容变更 → 替换旧版本（含旧原文与旧切片/向量）；任何情况下不得产生重复碎片。
- **FR-006**: 上传链路 MUST 保证元数据与原文的一致性：存储失败不得产生无文件的空文档记录；文档状态 MUST 如实反映"原文就绪/摄取进行中/成功/部分成功/失败"。
- **FR-007**: 上传触发的摄取 MUST 复用 005 摄取服务与全部既有语义（管线故障隔离、并发确定性、启动恢复），不重复实现切片/向量化逻辑。
- **FR-008**: 全部行为 MUST 可在 `./mvnw test` 中以真实数据库集成测试验证，向量化 MUST 可使用本地确定性嵌入模型替身（不依赖外部模型服务凭据）。
- **FR-009**: 任何日志与查询输出 MUST NOT 包含 api-key 等敏感配置（005 FR-010 红线延续）。

### Key Entities *(include if feature involves data)*

- **document_file（文件）**: 原文二进制（bytea）+ 文件名、内容类型、大小；与 document 一对一关联；存储路径/键对存储抽象层可寻址。
- **document（文档）**: 沿用 005 既有实体，本期增补与 document_file 的关联及文件级元信息（文件名、类型、大小）。
- **存储抽象层（OpenDAL Operator）**: 对上层暴露 save/load/delete/exists 语义的存储通道，v1 绑定 PG 实现；实体属性为后端无关的键（如 `document_file/<document_id>`）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 开发者通过一次上传调用即可完成"文档进入系统到可被检索"的闭环：上传一个 20KB Markdown 文档后 30 秒内，检索接口能用语义相关查询命中其片段。
- **SC-002**: 上传校验 100% 在入口处生效：超限或不支持的类型请求被拒绝且系统中查不到对应文档/文件残留。
- **SC-003**: 租户隔离 100% 成立：跨租户下载/查询/检索的泄漏用例通过率为 0。
- **SC-004**: 重复上传同内容文件时，文件与切片记录数不翻倍（重复数据产生率为 0）。
- **SC-005**: 下载返回的原文与上传内容逐字节一致（完整性校验通过率 100%）。
- **SC-006**: 全部验收场景可在 `./mvnw test` 中无外部凭据自动化通过。
- **SC-007**: 大文件上传中断后，仅重传缺失分块即可完成上传且最终原文逐字节一致（断点续传用例通过率 100%，已收分块零重传）。

## Assumptions

- 租户标识方式沿用 006 交付的 HTTP 租户定位约定（具体 header/参数形态在 plan 阶段与 006 契约对齐，本期不另立标准）。
- v1 仅支持纯文本/Markdown 上传（与 005 解析能力对齐）；PDF/Office 走后续独立 feature。
- 单文件上限默认 50MB、可通过配置调整；总量不设限（轻量级部署场景）。
- 文档标识 = 005 既有（租户内文档标题唯一性）语义，上传接口以标题作为文档标识载体，重复上传语义按 FR-005 执行。
- 本期不交付文档删除/更新管理接口（仅下载与查询）；删除语义涉及文件与向量的级联清理，留待后续 feature。
- 上传触发摄取为同步等待结果后返回（摄取本身为同进程服务调用）；异步化留待观测/性能需要时再评估。
