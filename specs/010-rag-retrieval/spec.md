# Feature Specification: RAG 检索问答与全链路可观测

**Feature Branch**: `010-rag-retrieval`

**Created**: 2026-10-01

**Status**: Draft

**Input**: User description: "架构必须全程可观测，RAG 文档摄入，切分，向量化等等，到最后检索是一套专业可扩展的架构"

## Clarifications

### Session 2026-10-01

- Q: 本期是否交付 HTTP 接口？ → A: 交付。检索接口与问答接口是 RAG 能力的第一个对外入口（005 已明确上传接口与问答接口同属后续 feature，本期即兑现问答/检索侧）；文档上传 HTTP 接口不在本期（摄取仍由应用内服务调用驱动，上传接口后续以薄端点接入）。
- Q: 检索请求如何定位向量表？ → A: 请求可显式指定粒度（摄取管线 key / 向量存储资源 key）；未指定时检索该租户全部已启用管线对应的向量表，按相似度归并取 topK。粗/细双粒度数据由此进入同一次问答，为"粗排定位、细排佐证"策略留口，具体合并策略 plan 阶段定。
- Q: 混合检索（全文+向量）是否纳入本期？ → A: 不作为默认交付。向量相似度检索 + 元数据过滤为本期基线；混合检索（langchain4j HYBRID 模式/外部检索器）作为可扩展点预留，接入决策归 plan 阶段（需评估中文分词配置成本）。

### Session 2026-10-14

- Q: 检索与问答的编排层用哪种形态？ → A: 自研显式有序阶段流水线（查询向量化 → 逐表检索 → 归并 → 提示词组装 → 模型调用），阶段之间提供可注册的拦截器扩展点；不使用 langchain4j 的 `AiServices`/`RetrievalAugmentor` 高层编排，但继续复用其底层组件（`EmbeddingStore`、`EmbeddingModel`、`OpenAiChatModel`）。
- Q: 拦截器扩展点的接口契约是只读观察还是可改写？ → A: 分两类职责分离的契约 —— 观察型（只读、数量不限、顺序无关）与增强型（可改写并可短路、须显式排序、数量受控），分开注册、分开执行。
- Q: 观测与"追踪"的落地形态是什么？ → A: 保持轻量，不引入 OpenTelemetry 或外部日志/追踪系统；观测与追踪日志**全部持久化到数据库观测表**，以统一记录入口查询。
- Q: 本期是否交付前端界面？ → A: 交付最小前端打通 —— 把 `/chat` 占位页换成可用的最简问答界面（提交问题、展示回答与引用片段、覆盖加载/空结果/失败三态）；会话历史管理、样式与无障碍深化不在本期。
- Q: 扩展点自身失败时主链路的语义是什么？ → A: 逐扩展声明失败语义（fail-open：仅记录并跳过；fail-closed：该阶段失败并进入降级），带默认值 —— 观察型默认 fail-open；增强型按性质默认（重排/过滤等可选优化 fail-open，改写查询/改写提示词等影响正确性者 fail-closed）。

## User Scenarios & Testing *(mandatory)*

> **本期范围说明**：交付"检索侧"——向量检索服务、RAG 问答（HTTP API）、贯穿摄取→切分→向量化→检索→问答的全链路可观测。文档摄取本身由 005 交付，本期不复述其功能，但观测模型必须覆盖 005 的各阶段（摄取/切分/向量化）并与本期观测统一。重排（RERANK）为可扩展预留点，不做默认交付。

### User Story 1 - 租户级向量检索服务 (Priority: P1)

开发者调用检索服务（或 HTTP 检索接口），提交（租户、查询文本、可选粒度/文档过滤、topK），系统用该租户自己的嵌入模型将查询向量化，在指定（或全部已启用）管线的向量表中做相似度检索并归并结果，返回带分数与来源元数据（文档、管线/粒度、片段序号、原文）的片段列表；两租户之间检索结果严格隔离。

**Why this priority**: 检索是 RAG 的另一半闭环——005 让文档进得来，US1 让内容搜得出。问答（US2）直接构建于其上。独立可测：确定性向量 + 元数据过滤 + 租户隔离都可在无外部凭据环境验证。

**Independent Test**: 两租户各摄取若干文档（005 能力）后，用构造的查询向量检索：断言命中本租户相关片段、带正确来源元数据、topK 与分数有序、过滤条件生效、查不到对方租户内容。

**Acceptance Scenarios**:

1. **Given** 租户 A 的细粒度表中有语义相关的片段，**When** 租户 A 检索对应语义的查询，**Then** 返回的片段属于租户 A、分数降序、带文档标识/管线 key/片段序号/原文，topK 生效。
2. **Given** 租户 A 与租户 B 拥有相似主题文档，**When** 同一查询分别检索，**Then** 各自只返回本租户片段，跨租户泄漏用例通过率为 0。
3. **Given** 检索请求指定文档标识过滤，**When** 检索，**Then** 只返回该文档的片段；指定粒度（管线 key）过滤时只检索对应向量表。
4. **Given** 未指定粒度，**When** 检索，**Then** 该租户全部已启用管线的向量表都被检索并按相似度归并。
5. **Given** 查询在库中无任何相关内容，**When** 检索，**Then** 返回空结果（或低于阈值的空结果），不报错、不返回他方数据。

---

### User Story 2 - RAG 问答接口 (Priority: P2)

用户通过 HTTP 接口向指定租户提问，系统将该租户自己的嵌入模型、向量表、聊天模型串成完整 RAG 链路：检索相关片段 → 组装带引用来源的提示词 → 调用租户自己的聊天模型生成回答 → 返回回答及所依据的片段清单。聊天模型不可达或检索为空时有明确、可读的失败/降级语义。

**Why this priority**: 问答是 RAG 面向最终用户的价值出口；依赖 US1 的检索，但作为独立接口可单独验收（检索可用替身数据驱动）。

**Independent Test**: 用确定性检索结果 + 替身聊天模型验证：提问 → 返回回答与引用片段清单；替身模型可断言收到的提示词中包含检索片段与来源标注；聊天模型缺失/不可达时返回明确错误而非裸堆栈。

**Acceptance Scenarios**:

1. **Given** 租户已摄取相关文档且聊天模型资源就绪，**When** 调用问答接口提问，**Then** 返回回答文本与引用片段清单（文档标识、片段、来源），回答生成所用的模型属于该租户。
2. **Given** 检索无结果，**When** 提问，**Then** 系统明确告知"知识库中未找到相关内容"（或等价降级语义），而非编造或裸报错。
3. **Given** 租户的聊天模型配置失效，**When** 提问，**Then** 返回可读的失败原因（不泄漏密钥），问答记录如实反映失败。
4. **Given** 同一问题分别向两租户提问，**When** 比较两次调用，**Then** 各自只基于本租户知识库作答（回答与引用均不跨租户）。

---

### User Story 3 - 全链路可观测 (Priority: P3)

运维与开发者能看清 RAG 全链路的每一环：一次问答从查询、向量化、检索（各表命中数/耗时/分数）、提示词组装到模型调用的每个阶段都有结构化记录可查；摄取侧（005 交付的摄取/切分/向量化执行记录）与检索侧使用统一的观测模型与查询入口；各环节有指标可聚合（量、延迟、失败率），慢调用与失败能在一处定位到租户与阶段。

**Why this priority**: 可观测是"专业架构"的交付标准，也是多租户平台排障的生命线；但它是横切保障，不阻塞 US1/US2 的功能闭环，故列 P3。

**Independent Test**: 构造一次完整问答后，断言：各环节结构化记录齐备且互相关联（同一 trace 串联）；摄取侧历史执行记录可在同一入口查询；聚合指标可被标准监控端点采集；日志中出现慢/失败时记录含租户与阶段定位信息且无密钥。

**Acceptance Scenarios**:

1. **Given** 完成一次问答调用，**When** 查询观测记录，**Then** 能看到各阶段（查询向量化、逐表检索命中/耗时、组装、模型调用/耗时、完成状态）的条目，以同一标识串联，含租户与所用资源 key。
2. **Given** 系统已有 005 产生的摄取执行记录，**When** 用统一入口查询，**Then** 摄取/切分/向量化阶段记录与本期检索记录同属一套模型，可按租户/文档/时间关联。
3. **Given** 问答调用失败（模型超时），**When** 查看记录与指标，**Then** 失败阶段、原因、租户可定位，失败计数进入聚合指标。
4. **Given** 监控端点暴露指标，**When** 采集，**Then** 能取到摄取量、检索量/延迟、问答量/延迟/失败率等租户可维度化的指标。

---

### Edge Cases

- 检索请求的粒度 key 不存在或指向未启用管线——明确失败并列出可用粒度，而非静默退化为全量检索。
- 租户没有任何已启用的摄取管线/向量表——检索返回空并说明原因；问答走"无知识"降级语义。
- 查询文本为空或超长——参数校验失败给出可读原因。
- 向量表在检索时被删/不可用——该表按失败记录，其余表结果照常返回（与 005 故障隔离语义一致）。
- 同一文档在粗/细两表均被检索命中——归并按分数降序、同分以 (documentId, pipelineKey, chunkIndex) 升序兜底，**不做跨表去重**（粗/细文本本就不同，"粗排定位、细排佐证"需两者并存；见 research.md R4）。
- 问答并发——租户间互不阻塞；同租户并发问答各自有独立对话上下文，不串话。
- 聊天模型返回空/异常内容——如实记录并返回可读失败，不把模型输出原样转义失败因。
- 观测记录本身写库失败——不得影响主链路（观测降级为仅日志，记录该降级事件）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供检索服务与检索 HTTP 接口：输入（租户、查询文本、可选粒度/文档过滤、topK、分数阈值），输出按相似度排序、带来源元数据的片段列表；检索 MUST 路由到该租户自己的嵌入模型与向量表（003 Router）。
- **FR-002**: 检索 MUST 支持元数据过滤（至少：文档标识、摄取管线/粒度 key）；过滤条件 MUST 以向量库原生能力执行（元数据随向量存储，004 契约 §3）。
- **FR-003**: 未指定粒度时，系统 MUST 检索该租户全部已启用管线对应的向量表并归并结果；归并 MUST 确定性（同输入同输出）。
- **FR-004**: 系统 MUST 提供问答 HTTP 接口：输入（租户、问题、可选会话标识），输出（回答、引用片段清单）；问答 MUST 使用该租户自己的聊天模型、嵌入模型与向量表。
- **FR-005**: 检索为空时问答 MUST 有明确降级语义（告知未找到相关内容），禁止无依据编造；模型不可达 MUST 返回可读失败原因。
- **FR-006**: 检索与问答 MUST 产生结构化观测记录：每个阶段（向量化/逐表检索/归并/组装/模型调用）一条，含租户、资源 key、耗时、数量、分数/状态与同一链路标识；005 的摄取执行记录 MUST 纳入同一观测模型与查询入口。观测与追踪日志 MUST 全部持久化到数据库观测表并以此为统一查询入口，MUST NOT 依赖外部日志聚合或分布式追踪系统（不引入 OpenTelemetry）；写库 MUST 为 best-effort，其失败 MUST NOT 影响检索/问答主链路。
- **FR-007**: 系统 MUST 暴露租户可维度化的聚合指标（摄取量、检索量与延迟、问答量/延迟/失败率），可被标准监控端点采集。
- **FR-008**: 观测记录与指标 MUST NOT 包含问题以外的敏感信息——尤其不得包含 api-key、聊天模型请求中的密钥（FR-008 红线延续）；问题文本的留存策略在 plan 阶段定义（默认留存，供排障）。
- **FR-009**: 检索/问答的各外部依赖故障 MUST 隔离并有明确语义：单表失败不影响其他表（005 语义延续）；聊天模型失败不影响检索服务本身。
- **FR-010**: 全部行为 MUST 可在 `./mvnw test` 中以真实数据库集成测试验证：检索用确定性向量、问答用替身聊天模型，不依赖外部模型服务凭据。
- **FR-011**: 检索策略 MUST 可扩展：重排（引用租户 RERANK_MODEL 资源）与混合检索以扩展点形式预留，新增策略不改变检索主流程与观测模型。
- **FR-012**: 检索与问答 MUST 实现为显式有序的阶段流水线（查询向量化 → 逐表检索 → 归并 → 提示词组装 → 模型调用），每个阶段为独立可替换组件。阶段之间 MUST 提供两组职责分离的扩展契约：**观察型**（只读阶段输入/输出与耗时，禁止修改；数量不限、顺序无关；承载日志、追踪、指标、审计）与**增强型**（可改写阶段输入/输出并可短路；须显式排序、数量受控；承载重排、过滤、提示词增强）。两者 MUST 分开注册、分开执行，观察型的执行位置 MUST 明确定义，其可观察到的数据语义 MUST 不因增强型的存在而产生歧义。接入上述扩展 MUST NOT 要求修改核心阶段实现。问答生成侧 MUST NOT 依赖 langchain4j 的 `AiServices`/`RetrievalAugmentor` 高层编排。

- **FR-013**: 前端 `/chat` MUST 由占位页替换为可用的最简问答界面：可提交问题、展示回答与引用片段（文档标识、片段序号、原文），并覆盖加载中/空结果/失败三态；MUST NOT 在本期引入会话历史管理、引用来源跳转、样式打磨与无障碍深化。

- **FR-014**: 每个扩展点 MUST 在注册时声明其失败语义 —— **fail-open**（失败仅记录并跳过该扩展）或 **fail-closed**（失败即该阶段失败并进入降级），且 MUST 有默认值：观察型默认 fail-open；增强型按性质取默认（重排、过滤等可选优化默认 fail-open；改写查询、改写提示词等影响结果正确性者默认 fail-closed）。该语义 MUST 可被降级/隔离用例验证。

**明确不在本期范围**（后续 feature 交付）：

- 重排（RERANK_MODEL）的实际接入（本期仅扩展点）
- 混合全文检索的默认启用（评估后决策）
- 前端界面的完整打磨（会话历史管理、引用来源跳转、样式与无障碍深化）
- 文档上传 HTTP 接口、文档管理/删除接口
- 多轮对话记忆的持久化与跨会话管理（本期会话上下文仅保证单次调用内/简单窗口语义，持久化方案后续 feature）
- 检索结果缓存、查询改写/ HyDE 等查询增强

### Key Entities *(include if feature involves data)*

- **检索记录（Retrieval Record）**: 一次检索的阶段化观测条目。属性：链路标识、租户、查询摘要、阶段、目标资源 key、命中数/分数统计、耗时、状态、失败原因、时间。
- **问答记录（QA Turn）**: 一次问答的完整观测与结果。属性：链路标识、租户、会话标识、问题、回答摘要、引用片段清单、各阶段引用、状态、耗时、时间。
- **检索请求要素**：租户、查询文本、粒度/文档过滤、topK、分数阈值（非持久化实体，契约要素）。
- **观测链路（Trace）**: 串联一次问答/摄取全程的标识与阶段条目集合（逻辑实体）。

## Success Criteria *(mandamental)*

### Measurable Outcomes

- **SC-001**: 常规开发环境（本地替身模型）下，知识库命中的问题从提问到返回答案 < 10 秒（含检索与生成）；纯检索 < 1 秒。
- **SC-002**: 跨租户检索/问答隔离测试通过率 100%——任何查询条件下返回的片段与引用均属于发起租户。
- **SC-003**: 100% 的检索与问答调用产生完整阶段记录（可串联成链路），记录断链用例通过率为 0。
- **SC-004**: 运维能在 1 分钟内从观测记录定位任意一次失败的阶段、原因与租户；从聚合指标看到各租户的量与延迟分布。
- **SC-005**: 检索为空、模型不可达、单表故障三类异常场景的降级/隔离语义测试通过率 100%。
- **SC-006**: 全部自动化测试在无外部模型凭据环境可运行且全绿；观测输出中检查不到任何密钥串。

## Assumptions

- 技术形态不沿用 langchain4j 官方 RAG 教程的高层编排（见 FR-012）：检索与问答由本项目自研的显式阶段流水线编排，阶段间以可注册拦截器承载日志/追踪/指标等横切关注点；仅复用 langchain4j 的底层组件（`EmbeddingStore`、`EmbeddingModel`、`OpenAiChatModel` 等）。检索请求参数经 Router 解析为该租户资源（EMBEDDING_MODEL / EMBEDDING_STORE / LLM）。
- 检索基线为向量相似度 + 元数据过滤（langchain4j Filter API，004 契约 §3 已确认 PgVector 支持）。**分数语义经实测修正**：`score ∈ [0,1]`，含义为 `(1 + cosine_similarity) / 2`（PgVector 硬编码余弦距离且无配置项，见 research.md R6）；阈值默认取 `0.70`（按 demo 语料校准，可由 `unirag.retrieval.default-min-score` 覆盖），由调用方按需指定 —— 填 `0.7` 等价于余弦相似度 `0.4`。
- 观测模型统一：005 的管线执行记录与本期检索/问答记录同属一套"阶段化记录"抽象，共享链路标识与查询入口；聚合指标基于 Micrometer（Spring Boot Actuator 已引入）。
- 业务数据与向量数据同库（uni_rag_db）延续既有决策；观测记录表随本期迁移新增。
- 会话上下文：本期为单次调用内的简单窗口（或不跨调用），持久化聊天记忆留待后续 feature（对应 langchain4j ChatMemoryStore 扩展点）。
- 检索归并默认策略、观测留存时长、问题文本留存策略、阈值默认值等细则**已由 plan 阶段定案**，见 `research.md` R3（留存 30 天 / 问题摘要留存）、R4（按分数归并 + 全序兜底键，不做跨表去重）、R7（阈值默认 0.70，可配置）。
