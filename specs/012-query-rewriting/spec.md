# Feature Specification: 查询改写（Query Rewriting）

**Feature Branch**: `012-query-rewriting`

**Created**: 2026-10-19

**Status**: Draft

**Input**: User description: "引入 QueryTransformer，可以复用现有扩展点：RetrievalRequest → QueryRewriteEnhancement（QUERY_EMBEDDING.beforeStage）→ 替换 retrievalQuery → QueryEmbeddingStage → VectorSearchStage → MergeStage。需要注意：保留原始 query 用于提示词，只替换用于检索的 retrievalQuery。否则 PromptAssemblyStage 会把改写后的问题当成用户原问题。"

## Clarifications

### Session 2026-10-19

- Q: 改写后的查询与原始问题各自用在哪里？ → A: 改写产物只作为**检索查询**参与向量化；提示词组装、回答、引用清单以及（启用时的）重排序一律继续使用**原始问题**。改写文本 MUST NOT 出现在"问题："位置，也不回显给用户当作其提问。
- Q: 改写失败时主链路如何处理？ → A: 回退到原始问题继续检索（fail-open）。原问题始终是有效输入，改写只是提升召回的优化；因此此处不沿用 010 对"影响正确性者 fail-closed"的默认值——回退原问题不会降低正确性。失败必须留痕且不让检索/问答返回服务端错误。
- Q: 本期是否支持多轮对话压缩、多查询扩展或假想答案（HyDE）？ → A: 不支持。本期输入只有当前问题，输出只有一条检索查询；不读取会话历史，不并行检索多条改写结果。
- Q: 请求方能否单独关闭改写？ → A: 可以。检索与问答请求均提供可选开关，省略时按租户默认；关闭后行为与改造前一致，响应结构不变。
- Q: 什么条件下改写真正生效？ → A: 全局开关开启、租户配置了可用的查询改写资源、本次请求未显式关闭，三者同时满足才调用改写；任一不满足即跳过，且不产生额外模型调用。
- Q: 改写默认使用哪个模型？ → A: 默认复用租户自己的主语言模型（对话/查询大模型）；若改写资源配置了独立的服务地址/模型/凭据，则以专用模型为准。`QUERY_REWRITE_MODEL` 资源的存在仍是租户级启用条件，资源配置可以为空（表示使用主语言模型）。

## User Scenarios & Testing *(mandatory)*

> **本期范围说明**：在既有检索/问答链路上引入**查询改写**能力：在查询向量化之前，用租户自己的改写模型把用户问题转写成一条更适合语义检索的查询，再用改写后的查询做向量检索与归并。改写模型默认复用租户主语言模型（对话/查询大模型），也可配置专用模型覆盖。原始问题保持不变，继续用于提示词、回答、引用与重排序。未配置改写资源或显式关闭时，行为与改造前完全一致。多轮对话压缩、多查询并行扩展、HyDE、混合检索不在本期范围。

### User Story 1 - 口语化问题也能检索到正确片段，且回答仍围绕用户原问题 (Priority: P1)

租户配置查询改写资源后，用户用口语、缩写、指代或不规范术语提问（例如"那个把文件切块的玩意儿怎么配"）。系统先把问题改写成更贴近知识库表述的检索查询，用它检索并归并片段，再用**原始问题**组装提示词、生成回答与引用。用户看到的回答与引用针对的仍是自己提出的问题，而不是某段被改写过的内部文本。

**Why this priority**: 这是本 feature 的核心价值：缩小用户口语与文档术语之间的语义鸿沟，同时不牺牲问答的可理解性与引用一致性。若改写文本泄漏进提示词，模型会把"改写后的问题"当成用户原问题作答，属于直接的用户可见错误。

**Independent Test**: 使用带人工相关性标注的查询集与确定性替身改写模型，验证：改写启用时向量检索收到的是检索查询而非原问题；提示词与回答生成收到的是原问题原文；未配置资源时行为与改造前逐字段一致。

**Acceptance Scenarios**:

1. **Given** 租户已配置可用的改写资源，且知识库中存在与用户意图相关的片段，**When** 用户以口语化/缩写方式提问，**Then** 向量检索使用改写后的检索查询并返回相关片段，回答与引用基于这些片段生成。
2. **Given** 一次启用了改写的问答，**When** 检查交给回答模型的提示词，**Then** "问题："位置是用户原始问题原文，改写文本只出现在检索侧，不作为用户问题出现。
3. **Given** 租户未配置改写资源，**When** 提问，**Then** 不调用改写模型，检索与问答结果与改造前逐字段一致。
4. **Given** 改写模型超时、不可达或返回非法内容，**When** 提问，**Then** 系统用原始问题继续检索并正常返回回答，链路中记录本次改写降级及原因。
5. **Given** 同一次问答启用了重排序，**When** 执行重排，**Then** 重排仍以用户原始问题为查询，不使用改写文本。

---

### User Story 2 - 检索接口同样受益且可精确控制 (Priority: P2)

调用检索接口的开发者可以在启用改写的情况下获得更好的召回；响应结构、字段语义与既有调用方式保持不变。调用方可以显式关闭改写以复现原始行为，也可以在请求中按需选择。改写后的文本只影响召回，不作为响应中的"查询"回显。

**Why this priority**: 检索接口是问答之外的直接消费者，复用同一套改写资源与链路；它独立可测，但不阻塞 P1 的问答价值。

**Independent Test**: 用确定性替身改写模型与固定知识库，对同一查询分别在开启/关闭改写、有/无租户资源下调用检索接口，断言检索输入、返回顺序与响应结构。

**Acceptance Scenarios**:

1. **Given** 租户已配置改写资源且请求未关闭改写，**When** 调用检索接口，**Then** 向量检索使用改写后的检索查询，响应结构与字段语义与改造前一致。
2. **Given** 请求显式关闭改写，**When** 调用检索接口，**Then** 直接使用原始查询检索，不调用改写模型。
3. **Given** 租户未配置改写资源，**When** 调用检索接口，**Then** 行为与改造前一致，不产生额外延迟或失败。
4. **Given** 检索请求带有粒度或单文档过滤，**When** 启用改写，**Then** 过滤条件仍按原请求生效，改写不扩大检索范围。

---

### User Story 3 - 改写可观测、可降级、可灰度评估 (Priority: P3)

运维与开发者能看到每次改写是否发生、耗时、状态、使用的模型资源与降级原因，并与同一次检索/问答的其他阶段共享链路标识；凭据不出现在日志、观测记录或错误信息中。上线前可在不改变检索结果的前提下观察改写效果，评估充分后再真正启用。

**Why this priority**: 改写新增一次外部模型调用与延迟，必须可观测、可降级、可灰度；它是 P1/P2 安全上线的前提，但不改变核心用户流程。

**Independent Test**: 构造改写成功、超时、返回非法内容、无资源四类场景，断言主链路状态、观测记录字段、降级原因与凭据零泄漏；构造观察模式场景，断言返回结果与关闭改写时一致。

**Acceptance Scenarios**:

1. **Given** 一次启用了改写的问答，**When** 查看观测记录，**Then** 能看到改写阶段的耗时、状态、模型资源标识、原始问题与检索查询的长度摘要，并与同链路其他阶段共享同一链路标识。
2. **Given** 改写超时或返回非法内容，**When** 查看记录与指标，**Then** 本次改写标记为降级，原因可定位，问答与检索仍返回可用结果。
3. **Given** 观察模式开启，**When** 执行检索或问答，**Then** 返回结果与关闭改写时逐字段一致，但观测记录中能看到本次改写的产物与耗时。
4. **Given** 任意改写成功或失败路径，**When** 检查日志、观测记录与错误信息，**Then** 看不到改写服务的 api-key、密码或配置原文。

---

### Edge Cases

- **改写结果与原始问题相同**：视为成功的无变化改写，正常记录，不重复调用或报错。
- **改写结果为空、纯空白或超过长度上限**：判定无效，回退原始问题并记录拒绝原因。
- **改写结果丢失原问题中的数值、日期、引号短语或代码片段等显式约束**：判定无效，回退原始问题并记录拒绝原因；不得用"看起来更通顺"的改写替换带约束的问题。
- **改写模型返回多段解释、前后缀或非查询内容**：判定无效并回退，不得把解释性文本送入向量化。
- **原问题超长（接近模型输入上限）**：跳过改写，直接使用原始问题，避免截断造成意图丢失。
- **中英文混合或外语问题**：改写必须保持原问题语言，不得无故翻译。
- **改写后检索为空**：按既有"未找到相关内容"语义返回；本期不自动改用原始问题二次检索。
- **请求带有单文档过滤或粒度过滤**：改写不得改变过滤范围。
- **观察模式下改写失败**：只记录降级，不影响返回结果。
- **并发请求**：每次请求独立改写，不共享可变状态或改写结果。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在查询向量化之前执行查询改写，并让向量检索使用改写后的**检索查询**；改写 MUST NOT 改变检索的粒度、文档过滤、topK、相似度下界或租户上下文。
- **FR-002**: 系统 MUST 同时保留**原始问题**与**检索查询**：提示词组装、回答生成、引用清单以及启用时的重排序 MUST 使用原始问题；原始问题 MUST NOT 被改写文本覆盖或替换。
- **FR-003**: 改写 MUST 以单条纯文本查询为产物：将口语化、缩写、指代、省略或不规范术语转写为更利于语义检索的表达，同时保留用户意图、实体、数值、时间、限定条件、语言与显式引用。
- **FR-004**: 改写 MUST NOT 回答问题、编造事实、来源或文档名，也 MUST NOT 引入原问题中不存在的硬性约束（如新增过滤条件或时间范围）。
- **FR-005**: 一次请求 MUST 最多产生一条检索查询；系统 MUST NOT 读取会话历史、生成多条并行查询或生成假想答案（HyDE）。
- **FR-006**: 系统 MUST 校验改写产物：空值、纯空白、超长、丢失显式约束或包含解释性内容时判定无效并回退原始问题，同时记录拒绝原因。
- **FR-007**: 改写失败（超时、不可达、限流、非法响应、资源缺失或失效）MUST 回退到原始问题继续检索；MUST NOT 使检索/问答返回服务端错误，MUST NOT 把改写故障暴露为问答失败。
- **FR-008**: 只有全局开关开启、租户配置了可用的改写资源（资源配置可复用租户主语言模型）、本次请求未显式关闭三者同时满足时才调用改写；任一不满足时 MUST 零额外模型调用，且结果与改造前逐字段一致。
- **FR-009**: 检索与问答请求 MUST 提供可选的改写开关（省略时按租户默认）；关闭后不调用改写模型，响应结构与字段语义保持不变。改写文本 MUST NOT 作为"用户问题"回显。
- **FR-010**: 改写 MUST 使用发起租户自己的模型资源；租户之间 MUST NOT 共享模型、凭据、提示词或改写结果。跨租户隔离用例通过率 MUST 为 100%。
- **FR-011**: 每次实际改写 MUST 产生可关联的观测记录，包含链路标识、租户、模型资源标识、状态、耗时、原始问题与检索查询的长度或脱敏摘要、拒绝或降级原因；记录 MUST 与同一次调用的其他阶段共享链路标识。
- **FR-012**: 系统 MUST 支持观察模式：在计算并记录改写结果的同时不改变检索与回答；观察模式下的改写失败 MUST NOT 影响主链路。
- **FR-013**: 相同输入、相同租户配置与确定性替身模型下，改写产物与最终检索结果 MUST 可复现；自动化测试 MUST NOT 依赖外部模型凭据或网络。
- **FR-014**: 改写 MUST NOT 改变租户隔离、向量检索、归并、重排序、提示词组装、引用展示与观测留存的既有契约；它只改变送入向量化的文本。

**明确不在本期范围**：

- 多轮对话压缩、基于会话历史的指代消解
- 多查询并行扩展、查询路由、HyDE、混合全文检索
- 改写策略的管理界面、自动提示词调优、A/B 分流管理
- 改写后检索为空时自动改用原始问题二次检索
- 前端展示改写过程或允许终端用户编辑改写结果
- 嵌入模型替换、向量索引调优或距离算子切换

### Key Entities *(include if feature involves data)*

- **改写资源（Query Rewrite Resource）**: 租户级可选模型资源，也是租户级启用开关。属性：资源标识、服务地址、模型标识、凭据、超时、提示词/策略版本、启用状态；每个租户至多一个主用改写资源。默认复用租户主语言模型（资源配置为空或省略连接字段），也可配置独立的服务地址/模型/凭据覆盖。是否真正启用还取决于全局开关与请求开关。
- **改写结果（Rewrite Outcome）**: 一次请求中的改写产物与状态。属性：原始问题、检索查询、是否观察模式、状态（成功/降级/跳过）、耗时、拒绝或降级原因。
- **改写记录（Rewrite Record）**: 一次实际改写的观测条目。属性：链路标识、租户、模型资源标识、状态、耗时、原始问题与检索查询的长度或脱敏摘要、原因、时间。
- **评测查询集（Evaluation Query Set）**: 用于验收改写效果的人工标注集合。属性：问题、租户/知识库、相关片段集合、不相关片段集合、问题类型（口语化/缩写/指代/术语不规范/普通）；不属于运行时持久化实体。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在不少于 20 条人工标注问题的评测集上，启用改写后 top-5 相关片段命中率相对基线提升不少于 10 个百分点；在"口语化/缩写/指代/术语不规范"子集上提升不少于 15 个百分点。
- **SC-002**: 100% 的启用改写的问答调用中，交给回答模型的提示词包含用户原始问题原文；改写文本仅用于向量检索，回答与引用不出现"把改写后的问题当成用户原问题"的情况。
- **SC-003**: 超时、不可达、限流、非法响应、资源缺失五类改写失败场景的降级成功率为 100%——检索/问答仍返回可用结果，不返回服务端错误，记录中可见降级原因。
- **SC-004**: 未配置改写资源或显式关闭改写的调用，其检索/问答响应与改造前逐字段一致，且改写模型调用次数为 0；相关回归用例通过率为 100%。
- **SC-005**: 在常规生产配置（真实改写模型）下，改写带来的额外延迟 p95 不超过 800 毫秒；专用改写资源的调用超时上限为 1.5 秒，复用主语言模型时沿用其超时配置且建议不超过 1.5 秒；启用改写后问答端到端 p95 不超过 3.5 秒，纯检索 p95 不超过 1.5 秒（不含冷启动）。
- **SC-006**: 100% 的启用改写的调用产生可关联的改写记录；日志、观测与错误信息中检查不到任何改写凭据。
- **SC-007**: 相同输入、租户配置与确定性替身模型下，改写产物与最终检索结果完全一致，确定性用例通过率为 100%。
- **SC-008**: 跨租户改写与检索隔离用例通过率为 100%——任一租户的改写不读取、不复用另一租户的模型、凭据或结果。

## Assumptions

- 本期无对话记忆，`sessionId` 仅透传；改写只基于当前问题，不做多轮压缩或跨轮指代消解。
- 改写资源复用租户现有的模型资源配置机制，不引入新的外部服务厂商；**默认复用租户主语言模型（对话/查询大模型）**，只有需要独立模型/凭据/超时时才配置专用连接信息；测试环境以确定性替身注入。
- "已配置改写资源"指租户存在可用的主用改写资源；资源的存在即租户级启用意图，但默认模型来自租户主语言模型，因此不会为曾经配置过该资源的租户引入第二套模型凭据。未配置该资源的租户行为不变，避免改造既有租户的默认行为。
- 默认参数：全局开关开启但无租户改写资源时不产生任何效果；专用改写资源超时默认/上限 1.5 秒，复用主语言模型时沿用其超时；检索查询长度上限 500 字符且不超过原问题的 2 倍；原问题超过 2000 字符时跳过改写。
- 请求级改写开关为可选布尔字段，省略时按租户默认（有资源即启用），与既有 `rerank` 开关的交互方式保持一致。
- 改写不改变既有请求校验、错误码、响应结构与观测留存周期；新增的观测阶段与既有阶段共用同一套记录与查询入口。
- 评测方式与 011 的重排评测共用"人工标注查询集"的组织方式，不新增运行时持久化实体。
- 改写效果依赖租户所选模型与提示词；首期以保守提示词（要求保留实体、数值与语言）和严格输出校验来控制风险，效果不足时通过更换模型或调整提示词迭代，而非放宽校验。
