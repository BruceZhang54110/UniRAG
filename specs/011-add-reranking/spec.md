# Feature Specification: 检索结果重排序（Reranking）

**Feature Branch**: `011-add-reranking`

**Created**: 2026-10-18

**Status**: Draft

**Input**: User description: "引入重排序"

## User Scenarios & Testing *(mandatory)*

> **本期范围说明**：在既有向量检索与 RAG 问答链路上引入可选的**重排序**能力：先扩大候选召回，再用租户自己的重排序模型对候选片段重新打分、排序和截断，使进入提示词与引用清单的片段更贴近问题。重排序是可选优化，未配置重排序资源的租户行为不变；查询改写、混合检索、嵌入模型迁移不在本期范围。

### User Story 1 - 问答只引用真正相关的片段 (Priority: P1)

租户配置重排序模型后，用户向知识库提问。系统先用向量检索取得比最终需要更多的候选片段，再用重排序模型判断每个候选“是否回答了这个问题”，只把重排后最相关的少量片段交给聊天模型，并在回答引用中排除“话题相似但没有回答问题”的片段。

**Why this priority**: 这是本 feature 的直接价值：当前问答会把向量分数刚过阈值的弱相关片段（例如问实时语音转写却引用 UniRAG 演示文档）带进提示词和引用清单。重排序直接提升回答可信度，是用户可感知的核心收益。

**Independent Test**: 使用带人工相关性标注的查询集与确定性替身重排序模型，验证：相关片段被保留并排在前面，弱相关片段被排除；未配置重排序资源时结果与改造前完全一致。

**Acceptance Scenarios**:

1. **Given** 租户已配置重排序模型且知识库中存在相关片段，**When** 用户提出一个可由知识库回答的问题，**Then** 返回的回答引用只包含重排后保留的片段，弱相关片段不出现在引用清单中。
2. **Given** 查询存在一个明显相关片段和若干“话题相似但不回答问题”的片段，**When** 执行问答，**Then** 重排后相关片段排在首位，弱相关片段被截断或过滤。
3. **Given** 租户未配置重排序模型，**When** 执行问答，**Then** 系统跳过重排，回答、引用与改造前保持一致。
4. **Given** 重排序服务不可用或超时，**When** 执行问答，**Then** 系统仍返回基于原向量排序的回答，并明确记录本次重排降级，不把重排故障暴露为问答失败。

---

### User Story 2 - 检索接口返回重排后的结果 (Priority: P2)

调用检索接口的开发者可以选择让结果经过重排序：接口先返回更宽的候选集，再按租户重排序模型的相关性分数排序并截断到请求的最终条数；响应结构与字段语义保持不变，调用方仍能拿到文档标识、片段序号、分数与原文。

**Why this priority**: 检索接口是问答之外的另一个直接消费者，重排能力复用同一套租户资源与候选处理逻辑；它独立可测，但不阻塞问答侧的 P1 价值。

**Independent Test**: 用确定性替身重排序模型对固定候选打不同分数，验证返回顺序、截断条数与响应结构；未启用重排时顺序与改造前一致。

**Acceptance Scenarios**:

1. **Given** 租户已配置重排序模型且请求启用重排，**When** 调用检索接口，**Then** 返回片段按重排相关性排序，且条数不超过请求的最终条数。
2. **Given** 请求显式关闭重排，**When** 调用检索接口，**Then** 返回原向量检索顺序，不调用重排序模型。
3. **Given** 租户未配置重排序模型，**When** 调用检索接口，**Then** 行为与改造前一致，不产生额外失败或额外延迟。

---

### User Story 3 - 运维可观测且可安全降级 (Priority: P3)

运维与开发者能够看到每次重排的候选数、保留数、耗时、状态与降级原因，并与同一次检索/问答链路关联；重排序调用的凭据不出现在日志、观测记录或错误信息中；重排异常不拖垮主链路。

**Why this priority**: 重排引入新的外部依赖与延迟，必须可观测、可降级、可灰度；它是 P1/P2 上线的前提保障，但不改变核心用户流程。

**Independent Test**: 构造重排成功、超时、返回非法结果三类场景，断言：主链路状态、观测记录字段、降级原因、凭据零泄漏。

**Acceptance Scenarios**:

1. **Given** 一次启用了重排的问答，**When** 查看观测记录，**Then** 能看到重排阶段的候选数、保留数、耗时与状态，并与同一次问答的其他阶段共享链路标识。
2. **Given** 重排服务超时或返回非法结果，**When** 查看记录与指标，**Then** 本次重排标记为降级，原因可定位，问答仍返回可用结果。
3. **Given** 任意重排成功或失败路径，**When** 检查日志、观测记录与错误信息，**Then** 看不到重排服务的 api-key、密码或配置原文。
4. **Given** 租户开启观察模式，**When** 执行检索或问答，**Then** 返回结果与未开启重排时一致，同时记录重排后的建议顺序与保留情况。

---

### Edge Cases

- 租户未配置重排序模型，或配置未启用——跳过重排，行为与改造前一致。
- 重排序服务超时、不可达、限流或返回错误——按 fail-open 降级为原向量顺序，记录降级原因，不影响问答/检索成功语义。
- 重排序返回的分数数量与候选数量不一致，或包含非法值——整批按失败处理并回退原顺序，不猜测缺失分数。
- 候选集为空——不调用重排序服务，直接返回空结果/进入“未找到相关内容”的问答降级。
- 重排后所有候选都低于保留阈值——返回空结果，问答明确告知未找到相关内容，不得用低相关片段硬答。
- 候选数超过重排序服务单次批量上限——分批打分后合并；合并结果 MUST 与单批处理在相同输入下一致。
- 同一条片段从多个粒度/多张表被召回——沿用既有归并语义（不跨表去重），重排后以确定性兜底键消除同分歧义。
- 重排模型资源配置非法或加载失败——该租户按未配置处理并记录失败原因；不得使应用启动失败或影响其他租户。
- 并发问答/检索——不同请求之间不得共享可变的候选或排序状态；同一输入重复执行 MUST 得到相同顺序。
- 查询或片段超长、超出重排序服务限制——按可读失败处理并回退原顺序，不得截断后静默改变语义。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持按租户配置可选的重排序模型资源，首期 MUST 至少支持 `BAAI/bge-reranker-v2-m3`；未配置或未启用时，检索与问答 MUST 保持改造前的行为与响应结构。
- **FR-002**: 启用重排时，系统 MUST 先召回比最终结果更多的候选片段，再对候选执行重排序，并只保留最终条数以内的片段；召回数量与最终条数 MUST 可配置。
- **FR-003**: 重排序 MUST 同时考虑用户查询与候选片段内容，而不是仅依据向量分数；排序结果 MUST 稳定可复现（相同查询、相同候选、相同模型得到相同顺序）。
- **FR-004**: 问答链路 MUST 使用重排后的片段集合组装提示词与引用清单；被重排排除的片段 MUST NOT 出现在引用中。
- **FR-005**: 检索接口 MUST 支持启用或关闭重排；启用时按重排相关性返回并截断，关闭或未配置时返回原向量顺序；响应字段与错误语义 MUST 保持向后兼容。
- **FR-006**: 重排序失败（超时、不可达、限流、响应非法、分数不完整）MUST NOT 导致检索/问答请求失败；系统 MUST 回退到原向量顺序，并将本次调用标记为降级。
- **FR-007**: 重排序 MUST 产生可关联的观测记录：至少包含链路标识、租户、候选数、保留数、耗时、状态与降级原因；聚合指标 MUST 能反映重排调用量、延迟与失败率。
- **FR-008**: 重排序资源与调用 MUST 按租户隔离；凭据 MUST 只通过租户资源配置提供，MUST NOT 出现在日志、观测记录、错误信息、测试断言或版本控制中。
- **FR-009**: 重排序的启用、召回数量、最终条数、超时与可选的相关性阈值 MUST 可配置，MUST NOT 需要修改代码才能调整。
- **FR-010**: 全部行为 MUST 可在真实数据库集成测试中验证；重排序 MUST 以确定性替身注入，测试 MUST NOT 依赖外部重排序服务凭据或网络。
- **FR-011**: 系统 MUST 支持灰度/观察模式：在不改变返回结果的前提下记录重排后的顺序与保留情况，供上线前评估；观察模式失败不得影响主链路。
- **FR-012**: 重排序 MUST NOT 改变向量检索、租户隔离、观测留存与引用展示的既有契约；它只影响候选的排序、过滤与最终条数。

**明确不在本期范围**：

- 查询改写、HyDE、混合全文检索的默认启用
- 嵌入模型替换、向量索引调优或距离算子切换
- 重排序模型的管理界面、自动阈值学习、多模型集成/投票
- 会话历史、引用跳转、前端样式与无障碍深化
- 对已召回候选之外的新文档进行二次检索

### Key Entities *(include if feature involves data)*

- **重排序模型资源（Rerank Model Resource）**: 租户级可选资源。属性：资源标识、服务地址、模型标识、凭据、超时、启用状态；一个租户可配置一个主用重排序模型。首期主用模型为 `BAAI/bge-reranker-v2-m3`。
- **重排候选（Rerank Candidate）**: 一次请求中的候选片段及其双重分数。属性：查询、片段标识与原文、原向量分数、重排相关性分数、最终是否保留。
- **重排记录（Rerank Record）**: 一次重排调用的观测条目。属性：链路标识、租户、模型资源标识、候选数、保留数、耗时、状态、降级原因、时间。
- **评测查询集（Evaluation Query Set）**: 用于验收重排效果的人工标注集合。属性：查询、租户/知识库、相关片段集合、不相关片段集合；不属于运行时持久化实体。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在不少于 20 条人工标注查询的评测集上，重排启用后“引用中出现的无关片段”比例不高于 10%，同时“相关片段被保留”的比例不低于 90%。
- **SC-002**: 典型弱相关问题（如询问实时语音转写，却召回到 UniRAG 演示文档）在启用重排后不再把该无关文档放入引用；相关文档仍在结果中。
- **SC-003**: 在 20–30 条候选的常规规模下，重排带来的额外延迟 p95 不超过 500 毫秒；用户从提问到看到回答的 p95 不超过 3 秒（不含首次冷启动）。
- **SC-004**: 重排失败场景的降级成功率为 100%——超时、不可达、限流或非法响应下，检索/问答仍返回可用结果，不返回服务端错误，且记录中可见降级原因。
- **SC-005**: 100% 的启用了重排的调用产生可关联的观测记录；日志、观测与错误信息中检查不到任何重排凭据。
- **SC-006**: 未配置重排序的租户，其检索/问答响应与改造前逐字段一致；相关回归用例通过率为 100%。
- **SC-007**: 相同输入重复执行（相同租户、查询、候选、模型配置）得到完全相同的排序与截断结果，确定性用例通过率为 100%。

## Assumptions

- 复用既有向量检索、RAG 问答与阶段化观测链路；重排作为检索与提示词组装之间的可选处理，不新建独立检索系统。
- 重排序模型是对“查询—片段”组合进行相关性打分的外部服务；首期主用模型为 `BAAI/bge-reranker-v2-m3`，托管端点、调用协议与部署形态由 plan 阶段定案，模型标识经租户资源配置，不在代码中硬编码。
- 租户配置了重排序资源后，检索接口默认启用重排，调用方可显式关闭；未配置资源的租户不做任何重排。上线前先以观察模式评估，观察模式不改变返回结果。
- 召回阶段可降低向量阈值以扩大候选，但重排分数与向量分数刻度不同，两者 MUST NOT 混用；向量阈值继续作为召回底线，重排阈值独立配置。首期重排阈值默认 0.5（BGE reranker relevance_score 的保守起点），可按模型/语料校准或关闭；最终条数仍由 `topK` 控制。
- 重排序只改变已召回候选的顺序、过滤与最终条数，不改变嵌入模型、向量表、距离算子或召回范围。
- 默认召回 20–30 条、最终保留 3–5 条；具体默认值由 plan 阶段结合延迟与成本定案。
- 评测查询集从现有 demo 知识库与真实问题中构建，人工标注相关/不相关片段；测试环境使用确定性替身，不依赖外部凭据。
- `topK` 继续表示调用方期望的最终条数；扩大召回是系统内部行为，不改变对外字段语义。
- 重排序模型不可用时按 fail-open 处理；这是可选优化，不应把外部服务故障升级为主链路故障。
- 既有引用展示格式不变，重排只影响引用集合与顺序。
- 术语说明：本 spec 中“重排”与“重排序”同义，统一指 reranking。

## Clarifications

### Session 2026-10-18

- Q: 未配置重排序资源时的默认行为？ → A: 完全沿用原行为；配置后默认启用，可通过请求或租户配置显式关闭。
- Q: 重排适用于哪些入口？ → A: 问答与检索接口共用重排能力；检索接口支持显式开关，问答侧默认使用重排结果。
- Q: 效果评测采用什么口径？ → A: 以“引用中无关片段比例”和“相关片段保留率”为主指标，不追求单一固定阈值下的绝对分数。
- Q: 采用哪个重排序模型？ → A: `BAAI/bge-reranker-v2-m3`，作为首期主用模型；托管端点与调用协议由 plan 阶段定案。
