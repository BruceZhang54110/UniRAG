# Feature Specification: 异步文档摄取任务

**Feature Branch**: `[008-async-document-ingestion]`

**Created**: 2026-10-07

**Status**: Draft

**Input**: User description: "Feature 008：异步文档摄取任务，保持轻量级，任务调度或者队列都使用pg；增加 document_ingestion_job 表；上传成功后只负责保存文件和创建 job；返回 202 Accepted 或 201 + QUEUED；增加任务状态查询接口；用 PostgreSQL FOR UPDATE SKIP LOCKED 领取任务；复用现有 IngestionService；增加失败重试和退避；增加最大重试次数；增加任务幂等键；新版本完成后再清理旧版本；增加 READY、FAILED、RETRYING 状态；增加“上传成功但摄取失败”的恢复测试。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 上传后排队处理文档 (Priority: P1)

开发者上传符合要求的文档后，系统先可靠保存原文并接受摄取请求，不要求客户端一直等待解析、分片和向量化完成。客户端收到任务标识和排队状态后，可继续执行其他工作。

**Why this priority**: 将文件上传与耗时不确定的摄取处理分离，避免摄取延迟或外部模型暂时不可用导致上传请求超时或重复提交。

**Independent Test**: 上传文档后，验证原文已持久化、摄取任务已创建且响应在摄取完成前返回；任务最终进入可查询的终态。

**Acceptance Scenarios**:

1. **Given** 租户有效且文件通过现有类型和大小校验，**When** 上传文档，**Then** 原文与文档元数据被持久化、任务被记录，响应包含任务标识及 `QUEUED` 状态，不等待摄取完成。
2. **Given** 原文持久化或任务创建失败，**When** 上传请求结束，**Then** 系统不得返回上传已成功，且不留下无法追踪的文档记录或孤立任务。
3. **Given** 客户端因网络问题重复提交同一文档版本，**When** 系统识别相同租户、文档、版本及内容指纹的请求，**Then** 不创建重复的有效摄取任务。

---

### User Story 2 - 查看摄取进度与可检索状态 (Priority: P1)

开发者可查询文档摄取任务的状态，区分原文已保存、正在处理、可检索、等待重试和最终失败，并查看安全、可操作的失败原因。

**Why this priority**: 上传成功不代表文档已进入索引。明确区分“文件已存储”和“文档可检索”，可避免调用方过早把文档视为可用。

**Independent Test**: 查询一个排队中的任务、一个成功任务和一个失败任务，确认返回正确状态、尝试次数及失败信息，且跨租户不可见。

**Acceptance Scenarios**:

1. **Given** 文档摄取任务尚未执行或正在处理，**When** 租户查询任务状态，**Then** 返回对应状态、当前处理阶段和任务标识。
2. **Given** 全部已启用管线处理成功，**When** 查询任务状态，**Then** 返回 `READY`，并报告可检索的文档版本及摄取结果。
3. **Given** 任务属于其他租户或不存在，**When** 查询任务，**Then** 返回统一的未找到语义，不泄漏其他租户任务是否存在。

---

### User Story 3 - 自动重试失败任务并安全替换文档版本 (Priority: P2)

系统遇到暂时性摄取失败时，按有限次数和逐步延长的间隔自动重试；重试耗尽后将任务标记为最终失败。更新文档时，只有新版本成功可检索后，旧版本才被清理或退出活动索引。

**Why this priority**: 模型服务、向量存储和网络的暂时故障不应要求用户重新上传，也不应在替换失败时丢失原有可用版本。

**Independent Test**: 注入可恢复和不可恢复的摄取故障，验证重试、等待时间、最大尝试次数、最终状态，以及新版本成功前后旧版本的可检索性。

**Acceptance Scenarios**:

1. **Given** 任务遇到暂时性故障且仍有重试额度，**When** 单次尝试失败，**Then** 任务进入 `RETRYING`，保存下次尝试时间，并按退避策略稍后再次执行。
2. **Given** 摄取持续失败达到最大尝试次数，**When** 最后一次尝试结束，**Then** 任务进入 `FAILED`，保留原文及安全可读的失败原因，不再自动重试。
3. **Given** 已有可检索的旧版本且新版本正在摄取，**When** 新版本失败，**Then** 旧版本继续可检索且原文不被删除；新版本达到 `READY` 后，系统才清理或停用旧版本。
4. **Given** 同一任务被多个工作进程同时轮询，**When** 任务被领取，**Then** 同一时刻最多一个工作进程执行该任务，其他进程可领取其他任务。

---

### Edge Cases

- 原文写入成功但任务创建失败：系统不得留下无法查询和恢复的“上传成功”记录；必须回滚或执行可验证的补偿。
- 工作进程领取任务后异常退出：任务在租约或超时后可重新领取，不永久停留在处理中。
- 重试过程中应用重启：任务状态、尝试次数和下次重试时间保持持久化。
- 同一文档新旧版本任务并发执行：旧任务不得覆盖更新版本的活动状态或误删新版本文件。
- 任务重复投递或工作进程重复执行：不得产生重复切片、向量或重复文档版本。
- 多条摄取管线部分成功：遵循现有摄取语义；只有符合项目既定“可检索就绪”条件时才标记 `READY`，失败原因不得包含凭据或配置原文。
- 任务已达最大重试次数：不再被普通轮询重新领取；显式人工重试是否纳入本期不在范围内。
- 取消任务、删除文档、批量导入和 PDF/OCR 解析不属于本期范围。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在上传成功前持久化原文、文档版本元数据和对应摄取任务；只有这三者均可追踪时才能向客户端确认上传已接受。
- **FR-002**: 上传接口 MUST 在任务持久化后立即返回异步接受结果，包含文档标识、文档版本、任务标识和 `QUEUED` 状态，不等待分片或向量化完成。
- **FR-003**: 系统 MUST 提供租户隔离的任务状态查询能力，至少返回状态、处理阶段、尝试次数、创建时间、最近更新时间及安全可读的失败信息。
- **FR-004**: 摄取任务 MUST 复用现有摄取服务和既有管线语义，不另行实现分片或向量化逻辑。
- **FR-005**: 系统 MUST 持久化任务领取状态，并确保同一任务不会被多个工作进程同时处理；工作进程异常退出后，过期领取的任务 MUST 可重新处理。
- **FR-006**: 系统 MUST 支持有限次数的自动重试及退避；最大尝试次数和退避参数 MUST 可配置或具有明确的默认值。暂时性失败等待重试时状态为 `RETRYING`，达到最大次数后状态为 `FAILED`。
- **FR-007**: 系统 MUST 为摄取任务建立幂等身份，至少基于租户、文档标识、文档版本和内容指纹；重复提交或重复执行 MUST 不得造成重复有效任务或重复切片/向量。
- **FR-008**: 文档 MUST 仅在对应版本摄取成功且满足现有可检索条件后标记为 `READY`；排队和处理中状态不得对调用方谎报为可检索。
- **FR-009**: 替换已有文档时，系统 MUST 保留旧可用版本，直到新版本达到 `READY`；新版本失败时旧版本保持可用，新版本就绪后才清理或停用旧版本。
- **FR-010**: 系统 MUST 对任务失败、重试和工作进程恢复保留足以审计和排错的信息；任何响应或日志 MUST NOT 暴露 api-key、数据库密码或未经筛选的配置原文/异常细节。
- **FR-011**: 系统 MUST 在自动化集成测试中验证上传被接受但摄取失败、自动重试后恢复或达到最终失败、应用/工作进程中断后的任务可恢复，以及旧版本安全切换。
- **FR-012**: 后台任务调度 MUST 满足项目轻量化约束，不要求新增独立消息代理或外部调度服务；任务必须在进程重启后仍可恢复。

### Key Entities *(include if feature involves data)*

- **摄取任务**：表示某租户某文档某版本的一次摄取工作，包含幂等身份、状态、处理阶段、尝试次数、下次执行时间、领取/租约信息及安全失败摘要。
- **文档版本**：表示原文及其摄取结果的不可混淆版本；同一文档可同时保留旧活动版本和待处理的新版本。
- **活动索引版本**：当前可用于检索的文档版本；仅在新版本满足就绪条件后切换。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在摄取处理仍未结束时，符合校验的上传请求仍能在 2 秒内返回任务标识和排队状态（不含文件传输时间）。
- **SC-002**: 对每个成功接受的上传，100% 可查询到对应的持久化摄取任务；不得出现已确认上传但无任务记录的情况。
- **SC-003**: 当摄取服务短暂失败并在配置的最大尝试次数内恢复时，至少 99% 的可恢复测试任务最终达到 `READY`，无需客户端重新上传原文。
- **SC-004**: 任一时刻同一摄取任务的并发执行数不超过 1；对重复投递的任务，重复切片和重复向量记录数为 0。
- **SC-005**: 新版本摄取失败时，100% 的替换测试中旧版本继续可检索；新版本达到 `READY` 后才发生活动版本切换和旧版本清理。
- **SC-006**: 应用进程重启后，所有未完成且未达到最大重试次数的任务均可在 1 分钟内重新进入调度或处理状态。
- **SC-007**: 最终失败任务的错误响应和日志敏感信息泄漏测试通过率为 100%。

## Assumptions

- 本功能复用 007 的上传、原文存储和租户定位能力，以及 005 的 `IngestionService`；不改变现有文本/Markdown 支持范围。
- 摄取队列和调度状态保存在 PostgreSQL 中，不引入 Kafka、RabbitMQ 或独立调度服务。
- 默认上传响应采用 `202 Accepted`，以明确表示文件已接受但索引尚未就绪；具体 HTTP 状态与响应兼容性在规划阶段确认。
- 默认采用有限重试及指数退避，并设置最大尝试次数；确切默认数值在规划阶段结合现有配置约定确定。
- `READY` 表示现有已启用摄取管线满足项目定义的可检索成功条件；部分成功是否可视为就绪沿用 005/006 的既有产品语义。
- “新版本完成后再清理旧版本”意味着旧版本在新版本摄取期间仍可被检索；本期不提供历史版本浏览接口。
- 本期不引入 OCR、多格式解析、人工审核、任务取消、手动重试 API 或独立消息代理。
