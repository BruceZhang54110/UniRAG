# Feature Specification: PGVector 向量存储落地

**Feature Branch**: `004-pgvector-embedding-store`

**Created**: 2026-09-27

**Status**: Draft

**Input**: User description: "004-pgvector-embedding-store：落地 PGVector 向量存储。通过 Flyway 迁移创建 pgvector 向量表（向量数据与业务数据统一存储于 PostgreSQL uni_rag_db），并完成按租户隔离的 PgVectorEmbeddingStore 装配——复用 003 多租户资源基座：EmbeddingStoreResourceProvider 加载各租户 EMBEDDING_STORE 资源（builder 字段与既有 EmbeddingStoreConfig 注释代码一致），使后续文档摄取（切分→向量化→入库）和检索可以直接使用各租户自己的向量存储。范围仅到"建表 + 组件装配 + 集成验证"，不含文档摄取和检索问答业务。"

## User Scenarios & Testing *(mandatory)*

> **本期范围说明**：本 feature 只交付"向量存储就绪"。文档摄取、检索问答属后续 feature。002 明确延期的"向量存储数据表初始化与向量存储组件装配"在本期完成；003 已交付的资源基座（Registrar / Router / Provider / 故障隔离）原样复用，不在本期修改其行为。

### User Story 1 - 应用启动即具备向量存储能力 (Priority: P1)

平台运维在全新环境（或已有业务库）部署应用时，应用启动过程中自动完成向量存储所需的数据库准备（向量扩展启用、基座结构就绪），无需任何手工 DDL 步骤；向量环境中不具备时给出可读失败原因或明确的预备指引。没有配置任何向量资源的租户环境同样正常启动。

**Why this priority**: 这是向量存储一切用途的前提——表结构没准备好，任何写入/检索都无从谈起；且环境准备是最容易"卡在新机器上"的环节，必须先可靠。

**Independent Test**: 在全新数据库上启动应用（或执行构建内迁移流程），向量扩展与基座结构自动就绪、健康检查 UP；在无向量扩展的环境按文档预备后同样通过；空配置环境启动成功。

**Acceptance Scenarios**:

1. **Given** 一个已安装 PostgreSQL 但未启用向量扩展的空数据库，**When** 应用启动执行迁移，**Then** 迁移自动启用向量扩展并完成全部基座结构，应用启动成功、健康检查 UP。
2. **Given** 向量扩展已存在、基座结构已存在（重复部署/重启），**When** 应用再次启动执行迁移，**Then** 迁移幂等通过，无报错。
3. **Given** 数据库账号无启用向量扩展的权限，**When** 应用启动执行迁移，**Then** 启动失败并输出可读原因及明确的操作指引（需先由管理员执行的操作），而非裸堆栈。
4. **Given** 没有任何租户配置向量资源（空配置），**When** 应用启动，**Then** 启动成功，健康检查 UP，不创建任何向量表。

---

### User Story 2 - 各租户向量存储按配置就绪且读写可用 (Priority: P2)

平台运营在数据库中为租户配置向量存储资源（所属库、表名、向量维度等）后，应用启动时为每个租户创建其专属的向量存储实例；开发者通过 003 的资源路由按"租户 + EMBEDDING_STORE + 标识"获取后，可直接写入文本向量并按相似度检索取回正确结果；两个租户之间的向量数据互不可见、互不串用。

**Why this priority**: US1 只解决"库就绪"；本故事让"租户的向量存储真正能用"，是后续文档摄取 feature 直接依赖的能力。依赖 US1 但不与其耦合——在已有向量环境的库上可独立验证。

**Independent Test**: 在真实向量数据库中为两个租户各配置一套向量资源并启动加载，通过资源路由获取两个租户各自的存储实例：各自写入带区分性内容的向量、各自检索，断言返回的是本租户写入的内容、查不到另一租户的内容；存储实例的参数（表名、维度）与配置一致。

**Acceptance Scenarios**:

1. **Given** tenant-a 配置了表 `embeddings_a`（维度 1024）、tenant-b 配置了表 `embeddings_b`（维度 1024），**When** 应用启动加载资源，**Then** 两个向量表均存在，通过路由获取的两个存储实例分别指向各自表，各自写入并检索均返回本租户内容。
2. **Given** 租户已配置的向量表在库中不存在且该租户配置允许自动建表，**When** 应用启动加载资源，**Then** 该表自动创建、维度与配置一致，资源加载成功。
3. **Given** 租户已配置的向量表在库中已存在（表结构由先前部署创建），**When** 应用启动加载资源，**Then** 表被复用而非重建，已有数据不受影响，资源加载成功。
4. **Given** 租户配置的向量表不存在且该租户配置禁止自动建表，**When** 应用启动加载资源，**Then** 该条资源加载失败并按 003 故障隔离规则记录（不影响其他租户），对应 Bean 不存在。
5. **Given** 两个租户各自写入了自己的向量数据，**When** 任一租户检索与另一租户内容相关、但自己库中不存在的语义，**Then** 返回空结果而非对方租户的数据。

### User Story 3 - 向量存储相关的配置防护与运维可见性 (Priority: P3)

当向量资源的配置存在隐患（如两个租户指向同一张表、维度非法）时，系统在加载期检出并明确处理：同名表归属不同租户属于隔离破坏风险，必须被检出、记录并按故障隔离规则处理，不能让两个租户静默共享一张表；运维能从日志与健康检查中定位每个向量资源的加载结果与失败原因。

**Why this priority**: 多租户隔离是平台核心价值（003 SC-002 的延续）；共享表静默串数据是最危险的事故类型。但作为"防护层"，它不阻塞 US1/US2 的主链路，故列 P3。

**Independent Test**: 构造两个租户配置同名向量表的数据集，启动后验证后加载者被记录为失败、其 Bean 不存在、其余资源（含先加载的同名表资源）正常；构造非法维度配置验证失败隔离；健康检查 details 中可看到向量资源的加载明细。

**Acceptance Scenarios**:

1. **Given** tenant-a 与 tenant-b 配置了相同的向量表名（不同租户），**When** 应用启动加载资源，**Then** 先加载者正常注册，后加载者记错误日志（含两个租户标识与表名）并按故障隔离跳过，两者 Bean 不指向同一存储。
2. **Given** 某租户向量资源配置了非法维度（非正整数），**When** 应用启动加载资源，**Then** 该条资源按 003 故障隔离规则记录失败，其他资源正常。
3. **Given** 向量资源加载完成（部分成功或全部成功），**When** 运维查看健康检查，**Then** details 中能看到向量资源的加载数量、失败数量与逐条失败明细（租户、类型、标识、原因），且不含数据库密码等敏感信息。

### Edge Cases

- 向量扩展在部分托管 PostgreSQL 上不可用（或无超级用户权限）——迁移给出可读失败与文档化的人工预备步骤；开发/测试环境允许通过配置关闭自动建表走降级验证（沿用 003 R12 约定）。
- 向量表已存在但维度与配置不一致——按 Provider 构建规则处理（构建期不静默改表现存结构，冲突按配置失败记录，具体行为在 plan 阶段定义）。
- 表名包含非法字符或与数据库保留字冲突——沿用 003 命名规范化规则处理或按配置失败记录。
- 向量资源的数据库连接指向与业务库不同的另一个 PG 实例——允许（配置独立），故障隔离与日志规则不变；敏感信息（密码）不入日志。
- 同一租户配置了多个向量存储资源（不同 key）——各自独立建表/校验，互不干扰。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 通过版本化迁移在目标 PostgreSQL 库启用向量扩展并完成向量存储基座结构准备；重复执行 MUST 幂等。
- **FR-002**: 当迁移因权限等原因失败时，系统 MUST 失败并输出可读原因与明确的人工预备指引。
- **FR-003**: 系统 MUST 为每个启用的租户向量资源配置创建独立的向量存储实例（复用 003 资源基座，Bean 命名与路由规则不变），实例的库、表、维度参数与配置一致。
- **FR-004**: 系统 MUST 保证不同租户的向量数据相互隔离：不同租户配置的向量表 MUST 不同；检测到不同租户配置同名表时，后加载的 MUST 按故障隔离规则记录失败并跳过，不得共享存储。
- **FR-005**: 向量表不存在且配置允许自动建表时，系统 MUST 自动建表且维度与配置一致；向量表已存在时，系统 MUST 复用现有表、不得破坏已有数据；配置禁止自动建表且表不存在时，该条资源 MUST 按故障隔离规则记录失败。
- **FR-006**: 全部向量资源 MUST 可通过 003 的健康检查机制查看加载数量、失败数量与逐条失败明细（租户、类型、标识、原因）。
- **FR-007**: 任何日志与健康检查输出 MUST NOT 包含数据库密码等敏感配置（延续 FR-008 红线）。
- **FR-008**: 无向量资源配置（空配置）环境下，应用 MUST 正常启动，迁移与加载均不产生错误。
- **FR-009**: 本 feature 的行为 MUST 全部可在 `./mvnw test` 中以真实 PostgreSQL 集成测试验证，无需任何外部模型服务凭据（写入/检索测试使用本地构造的确定性向量）。

**明确不在本期范围**（后续 feature 交付）：

- 文档摄取、切分、向量化入库管线
- 向量检索与检索增强问答链路及业务 HTTP 接口
- 向量维度与嵌入模型输出维度的自动校验/对齐（本期由配置方保证一致）
- 向量数据的删除、更新与生命周期管理

### Key Entities *(include if feature involves data)*

- **向量表（Embedding Table）**: 一个租户向量存储资源的物理载体。属性：所属库、表名、向量维度、结构约定（标识、向量、原文、元数据）。命名应能体现租户归属。
- **向量记录（Embedding Entry）**: 向量表中的一条记录。属性：唯一标识、向量数据、关联原文、元数据（JSON）。
- **租户向量存储配置**: 003 已定义的租户资源配置在 EMBEDDING_STORE 类型的具体化（host/port/database/user/password/table/dimension/create-table），本期不改动其 Schema。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 运维在全新数据库部署应用时，零手工 DDL 步骤完成向量环境准备；应用一次启动成功、健康检查 UP。
- **SC-002**: 在配置两个租户向量资源的测试中，100% 的写入/检索用例返回本租户数据，跨租户数据可见性测试通过率为 0 泄漏（100% 隔离）。
- **SC-003**: 不同租户配置同名向量表时，100% 被检出并按隔离规则处理，两租户共享存储的用例通过率为 0。
- **SC-004**: 全部自动化测试在无外部模型凭据环境可运行且全绿；重复启动（迁移重入）不产生错误。
- **SC-005**: 运维能在 1 分钟内从健康检查或日志定位任一向量资源的加载结果与失败原因，且输出中检查不到任何密码串。

## Assumptions

- 沿用 002 的存储决策：向量数据与业务数据统一存储于 PostgreSQL（`uni_rag_db` 同一实例），向量能力由 pgvector 扩展提供；各租户向量资源也允许配置指向其他 PG 实例（配置独立、语义不变）。
- 003 多租户资源基座已交付并按其原语义使用：向量资源是 `tenant_resource_config` 中 `resource_type = EMBEDDING_STORE` 的记录，Provider 的 JSON Schema（host/port/database/user/password/table/dimension/create-table）本期不变。
- 向量表为"每租户资源一张表"，表名由配置显式指定并应含租户标识；表由存储组件在加载期创建/复用（Flyway 只管理扩展与全局基座结构，不管理逐租户动态表）。
- 启用向量扩展需要数据库管理员权限；迁移脚本使用幂等语句，无权限时按 quickstart 文档提供的人工步骤预备。
- 向量维度与租户嵌入模型输出维度的一致性由配置方保证（写入维度不匹配的数据属于后续业务 feature 的校验范畴）。
- 测试沿用 003 约定：真实本地开发库 `uni_rag_db` + 每测试类全局唯一租户码；本地库已安装 pgvector 扩展。
