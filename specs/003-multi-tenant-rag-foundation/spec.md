# Feature Specification: 多租户 RAG 资源基座

**Feature Branch**: `003-multi-tenant-rag-foundation`

**Created**: 2026-09-16

**Status**: Draft

**Input**: User description: "实现面相多租户的RAG 应用， AI模型，嵌入模型等其他资源。每个租户都不同，配置也不同。初步实现多租户资源基座，用于加载不同租户的模型Bean 。代码中已有部分代码"

## Clarifications

### Session 2026-09-16

- Q: 资源实例（Bean）的命名规则应采用哪种？ → A: `{resourceType}_{tenantId}_{key}`（如 `embeddingModel_tenantA_openai`），与目标架构图一致；现有代码常量 `BEAN_NAME_PREFIX="tenant"` 需相应调整。
- Q: 通过 Router 查询不存在的资源时，应返回什么失败信号？ → A: 抛专用异常（携带 tenantId/type/key），调用方必须显式处理。
- Q: `getPrimary(tenantId, type)` 的行为规则是什么？ → A: 无 primary 时若该租户该类型仅有唯一实例则回退返回它，否则抛专用异常；同类型多条 primary 属配置错误，加载时记错误日志并取记录 ID 排序首个作为 primary，不阻塞启动。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 应用启动时按租户加载各自的模型资源 (Priority: P1)

平台运营方在数据库中为多个租户分别配置了 AI 聊天模型、嵌入模型、向量存储等资源的连接参数。应用启动时，系统读取所有已启用租户的资源配置，为每个租户创建其专属的资源实例（如各自的模型客户端、嵌入模型、向量存储），并以可区分的名称注册到运行时中，供后续 RAG 流程使用。

**Why this priority**: 这是多租户 RAG 应用存在的前提——没有按租户隔离加载资源的能力，任何上层 RAG 功能（问答、检索、重排）都无法工作。这是最小可用产品。

**Independent Test**: 在数据库中配置两个租户、各自不同的模型参数，启动应用后可验证两个租户各自的资源实例均已创建，且参数各自生效（例如各自指向不同的模型服务端点）；只配置一个租户时应用同样正常启动并加载该租户资源。

**Acceptance Scenarios**:

1. **Given** 数据库中存在两个已启用租户（tenant-a、tenant-b），各自配置了不同的聊天模型与嵌入模型参数，**When** 应用启动，**Then** 系统中出现 4 个资源实例，分别归属 tenant-a 和 tenant-b，且每个实例使用的是该租户自己的配置参数。
2. **Given** 数据库中没有任何租户或没有任何资源配置，**When** 应用启动，**Then** 应用正常启动，不创建任何租户资源实例，不报错。
3. **Given** 一个已启用租户配置了聊天模型和嵌入模型但未配置向量存储，**When** 应用启动，**Then** 该租户已有的资源实例正常创建，缺失的资源类型不阻塞启动。

---

### User Story 2 - 按租户获取对应的模型资源 (Priority: P2)

开发者在编写 RAG 业务流程时，能够根据"租户标识 + 资源类型 + 资源标识"获取到该租户专属的资源实例（如该租户的聊天模型），从而保证任何业务调用都路由到正确的租户资源上，租户之间互不串用。

**Why this priority**: 加载资源之后必须有一种可靠的取回方式，否则加载的资源无法被业务使用。依赖 P1 但不与其耦合，可通过独立的获取接口测试。

**Independent Test**: 在已加载两个租户资源的运行环境中，通过"租户 + 资源类型 + 资源标识"分别取回两个租户的同类型资源，验证取回的资源是各自租户的实例；对不存在的租户或资源标识，能收到明确的失败信号而非空指针或错误的他人资源。

**Acceptance Scenarios**:

1. **Given** tenant-a 与 tenant-b 各自已加载名为 "default" 的聊天模型资源，**When** 分别按 (tenant-a, 聊天模型, "default") 和 (tenant-b, 聊天模型, "default") 获取，**Then** 返回的是两个不同租户的各自实例。
2. **Given** 系统中不存在租户 tenant-x 的任何资源，**When** 按 (tenant-x, 聊天模型, "default") 获取，**Then** 系统返回明确的"资源不存在"失败信号。
3. **Given** 租户配置了同类型下的多个资源（如两个嵌入模型，key 分别为 "default" 与 "small"），**When** 按不同 key 获取，**Then** 返回各自对应的资源实例。

---

### User Story 3 - 单租户配置故障不影响其他租户 (Priority: P3)

当某个租户的一条资源配置存在错误（如参数缺失、格式非法、连接不通）时，系统只跳过或标记该条资源，其余租户的全部资源以及该租户其余正常的资源照常加载和使用。

**Why this priority**: 多租户平台的核心价值之一是故障隔离；但作为"初步基座"，可以先做到加载期隔离，运行时重试/热更新可留待后续迭代。

**Independent Test**: 构造一个租户含非法配置、另一个租户配置全部合法的数据集，启动应用后验证合法租户资源全部可用、非法资源被记录且不影响其他资源加载。

**Acceptance Scenarios**:

1. **Given** tenant-a 的聊天模型配置缺少必填参数，tenant-b 配置全部合法，**When** 应用启动，**Then** tenant-a 的该条资源创建失败并被记录，tenant-a 的其他资源与 tenant-b 的全部资源正常创建。
2. **Given** 一条资源配置创建失败，**When** 加载流程结束，**Then** 日志中包含失败资源所属的租户、资源类型、资源标识及失败原因，便于运维定位。

---

### Edge Cases

- 数据库中两个租户配置了相同的"资源类型 + 资源标识"——资源标识仅在租户内唯一，实例按租户隔离，不同租户同名互不影响。
- 资源配置存在但所属租户被停用（disabled）——该租户全部资源不加载。
- 某资源类型的配置存在，但系统没有对应的支持插件（Provider）——记录告警并跳过，不影响其他资源。
- 资源配置中的敏感信息（API Key 等）——假定以加密或安全存储方式保存于配置存储中，明文不出现在日志里。
- 资源标识或租户标识包含非法字符时——生成的资源实例命名需做规范化处理以避免命名冲突。
- 同租户同类型配置了多条 primary 资源——属配置错误：加载时记录错误日志，取记录 ID 排序首个作为 primary，不阻塞启动（见 FR-011）。
- 同租户同类型无任何 primary 且仅有唯一实例——getPrimary 回退返回该唯一实例；有多个实例时抛专用异常（见 FR-011）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在启动时读取配置存储中所有已启用租户的资源配置记录（每条记录包含：所属租户、资源类型、资源标识、是否主资源、JSON 配置体、启用状态）。
- **FR-002**: 系统 MUST 为每条已启用的资源配置创建一个资源实例，资源类型至少覆盖：聊天模型（LLM）、嵌入模型、向量存储（Embedding Store）；设计上 MUST 允许后续扩展新的资源类型（如重排模型）。
- **FR-003**: 系统 MUST 保证同一租户内的资源按"资源类型 + 资源标识"唯一；资源实例 MUST 归属到其所属租户，租户之间不得共享或串用实例。
- **FR-004**: 系统 MUST 提供按"租户标识 + 资源类型 + 资源标识"查询已加载资源实例的路由接口（TenantResourceRouter）；查询不存在的资源时 MUST 抛出专用异常（携带 tenantId/type/key），调用方必须显式处理，全系统语义一致。
- **FR-005**: 系统 MUST 将资源创建逻辑按资源类型拆分为可插拔的插件（Provider）：每种资源类型一个插件，插件负责解析该类型的 JSON 配置并创建对应实例。
- **FR-006**: 当某条资源配置创建失败时，系统 MUST 记录包含租户、资源类型、资源标识、失败原因的日志，且 MUST NOT 因此中断其余资源及租户的加载。
- **FR-007**: 系统 MUST 对无资源配置、无启用租户的情况保持启动成功（空载启动）。
- **FR-008**: 系统 MUST NOT 在日志中输出配置中的敏感信息（API Key、密钥等）。
- **FR-009**: 系统 MUST 暴露健康检查或等价机制，使运维能够确认资源基座已就绪（即使处于空载状态）。
- **FR-010**: 配置解析失败的资源 MUST 不能部分注册——即一条记录要么完整创建成功，要么完全不创建。
- **FR-011**: 系统 MUST 支持按"租户标识 + 资源类型"获取该租户的主资源（getPrimary）：无 primary 标记且该类型仅一个实例时回退返回该实例；无 primary 且有多个实例时 MUST 抛专用异常；同类型存在多条 primary 属配置错误，加载时 MUST 记录错误日志并取记录 ID 排序首个作为 primary，不阻塞启动。

### Key Entities *(include if feature involves data)*

- **租户（Tenant）**: 平台中的一个客户/组织。属性：租户标识、名称、启用状态。
- **租户资源配置（Tenant Resource Config）**: 一条声明"某租户拥有某类型某标识的资源及其参数"的记录。属性：记录ID、所属租户、资源类型（聊天模型/嵌入模型/向量存储/重排模型）、资源标识（租户内同类型唯一）、是否主资源、JSON 配置体、启用状态。
- **资源实例（Tenant Resource Bean）**: 启动时由资源配置实例化出的运行时对象（如某个租户的聊天模型客户端），以"租户 + 类型 + 标识"可寻址。
- **资源插件（Resource Provider）**: 按资源类型实现资源解析与实例创建逻辑的扩展点。
- **资源路由（TenantResourceRouter）**: 业务侧获取资源实例的统一入口，按"租户 + 类型 + 标识"（或主资源）返回实例，资源不存在时抛专用异常。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 配置 N 个租户（N ≤ 100）各自全套资源（聊天模型、嵌入模型、向量存储）后，应用一次启动完成全部资源加载；任意单条资源创建失败不得使整体启动时长超过全部正常时的 10%。
- **SC-002**: 100% 的资源获取请求按"租户 + 类型 + 标识"返回正确的租户实例，跨租户串用实例的测试用例通过率为 100%。
- **SC-003**: 任意单条资源配置错误时，其余资源加载成功率保持 100%，且运维能在 1 分钟内从日志定位到出错的租户与资源。
- **SC-004**: 新增一种资源类型的支持时，无需修改加载主流程代码，仅需新增一个插件实现（以代码评审或演示验证扩展性）。
- **SC-005**: 空配置环境下应用启动成功率 100%（不产生阻塞启动的错误）。

## Assumptions

- 租户与资源配置存储于关系型数据库（项目已含 Flyway 迁移脚本与 MyBatis-Plus 实体），配置变更目前需重启生效；热更新不在本期范围。
- 资源实例在启动时统一创建，注册到应用运行时容器中，命名规则为 `{resourceType}_{tenantId}_{key}`（如 `embeddingModel_tenantA_openai`，见 Clarifications Session 2026-09-16 Q1），对包含非法字符的标识做规范化处理。
- 本期仅实现"加载 + 获取 + 故障隔离"基座；基于这些资源的检索、问答、RAG 编排属于后续 feature（002 号特性已涉及 langchain4j RAG）。
- 资源配置的 JSON 配置体结构由各资源类型的插件自行定义并校验；基座只负责透传。
- 敏感配置（API Key）假定在存储侧已加密或以安全配置中心方式注入；本期只需保证不明文打日志。
- 现有代码中的 `TenantResourceRegistrar.run()` 为空实现、`TenantResourceConfig` 缺少访问器、Bean 命名前缀常量 `BEAN_NAME_PREFIX="tenant"` 与目标命名规则不一致，均视为待本特性完成/修正的半成品基座。
